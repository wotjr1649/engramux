# Engramux 1.0 — Design

**rev.4** · 2026-08-27 · supersedes rev.1–rev.3 and `docs/chatgpt/Engramux_Final_Architecture_and_Execution_Plan_ko.md`

This document holds decisions, invariants, and measurements. It does not hold Go signatures, DDL,
or a package tree — code owns those, and the two earlier revisions were discarded because they
tried to own them and got them wrong. Every factual claim below is either marked **[verified]**
with a way to reproduce it, or **[unverified]**. Nothing in between.

---

## 1. What we are building

A Windows-first service that captures Claude Code and Codex session hook events into SQLite and
serves them back through FTS5 and MCP. One service per Windows user multiplexes every concurrent
session across every project.

The differentiator is automatic hook capture. `engram` (Go, SQLite+FTS5) requires the agent to
call `mem_save` explicitly and is MCP-stdio only. `claude-mem-lite` captures hooks but has no
Windows support. `thedotmack/claude-mem` does both and breaks constantly on Windows.

**Full behavior parity with claude-mem is not a 1.0 goal**, and its architecture is never a model —
that is the part that fails on Windows. Adopting an individual compatible behavior later is fine when
a spec asks for it; migration and interoperability are legitimate goals beyond 1.0.

## 2. Scope decisions

| Decision | Value |
|---|---|
| Purpose | Personal daily driver *and* public OSS product |
| Hosts | Claude Code and Codex, both in 1.0 |
| Events | The 11-event intersection only (Claude has 31 ⊃ Codex 11, Codex-only 0) |
| claude-mem migration | **Not in 1.0.** Start with an empty database |
| LLM summarization | **Not in 1.0.** No `Generator` or `Embedder` interface either — an unused interface is a design commitment we have not earned |
| Trust boundary | A single Windows user SID is **inside** the boundary |
| Event ordering | Partial order. Wall-clock time is not an ordering key |
| Secrets | Detected and tagged at ingest, never erased from the database. Filtered at every egress (§6.1) |
| Fixtures | Synthesised. Shape copied from real captures, every value invented (§6.2) |
| Search target | **The raw event text**, not extracted titles (§5.7) |
| Context re-injection | **1.0 is pull-only.** SessionStart emits nothing (§5.8) |
| Process model | One persistent service; relays are per-event and transient (§5.1) |

## 3. Invariants

These must hold at every commit. A change that breaks one is a design change, not a bug fix.

| # | Invariant |
|---|---|
| **I-01** | Exactly one persistent process per Windows user. Sessions and projects are rows, not processes |
| **I-02** | No per-session process. The service spawns a child only where a decision in §5 says so, and every such child is created with the no-window flag |
| **I-03** | A hook never blocks its host. The relay exits 0 on every path, including panic |
| **I-04** | A captured event is never silently dropped. If it cannot be delivered it is spooled; if it cannot be classified it is stored as `unknown` |
| **I-05** | Every event carries an idempotency key minted at capture time and reused across every retry |
| **I-06** | Ordering is partial. Two events are ordered only when the ingest path establishes it |
| **I-07** | The service holds the database exclusively. No other process opens it — ever, including read-only |
| **I-08** | Every CLI read travels over the pipe. There is no read-only fallback (I-07 forbids one) |
| **I-09** | The singleton is enforced by `ListenPipe` exclusivity on a **fixed** pipe name, plus Task Scheduler's `IgnoreNew` |
| **I-10** | A secret is **tagged, not destroyed**, on the way into the database. It never leaves the machine untagged: every egress — log, search result, export, fixture — filters on the tag (§6.1) |
| **I-11** | Every pragma is read back at startup and compared against its expected value. A mismatch fails startup |
| **I-12** | Host detection reads the payload, never argv |
| **I-13** | MCP binds `127.0.0.1` and requires bearer authentication |
| **I-14** | An event whose host×event cell is not explicitly enabled is stored but not parsed |

## 4. Host contract

This section is not ours to decide. It records what the two hosts actually do.

### 4.1 The 11-event intersection

`SessionStart` · `SessionEnd` · `UserPromptSubmit` · `PreToolUse` · `PostToolUse` · `Stop` ·
`SubagentStart` · `SubagentStop` · `PreCompact` · `PostCompact` · `PermissionRequest`

Claude Code exposes 31 events; Codex exposes 11; the Codex set is a subset. 1.0 handles the
intersection and nothing else.

### 4.2 Invocation shape

Claude Code takes `command` plus an `args` array (exec form, no shell). Codex takes
`commandWindows` as a single string. Claude Code has no `commandWindows` key; a hook that only
sets it is never invoked.

### 4.3 Host detection

The relay is told nothing about which host launched it — argv is not trustworthy because the same
binary path appears in both hosts' configuration. Detection reads the payload:

1. `prompt_id` or `effort` present → Claude Code
2. `model` or `turn_id` present → Codex
3. Neither → fall back to the directory component of `transcript_path` (`.claude` vs `.codex`)

**[verified]** Across 901 real captures, steps 1–2 classify 887 and step 3 classifies 13. One
capture remains unclassifiable — a synthetic self-test payload with `session_id == "selftest"` and
no `transcript_path`, which §7.5 requires filtering. After that filter: **900/900**.

A two-step rule (dropping `transcript_path`) loses **all 13 Codex `SessionEnd` events**. rev.2
specified the two-step rule and called it exhaustive; it was not.

### 4.4 Payload shape differences

**[verified]** `tool_response` on `PostToolUse` has different types per host:

| Host | Type | Count | Error keys |
|---|---|---|---|
| Claude Code | object | 310/310 | `stderr` and `interrupted` present in **241/310** only |
| Codex | string | 24 | — |
| Codex | array | 15 | — |

Any parser that assumes an object is wrong for every Codex event and for 69 Claude events. An
error-classification rule written against `tool_response.interrupted` never fires on Codex.

Reproduce: iterate `.capture/fixtures-raw/*PostToolUse*.json` and tabulate the type of
`payload["tool_response"]`.

### 4.5 stdout contract

**[verified]** Empty stdout is accepted by all 11 events on both hosts, confirmed across 901
captures. Since 1.0 is pull-only (§5.8), the relay writes nothing on any event.

## 5. Architecture decisions

Each entry states the decision, why, and what it costs.

### 5.1 Two binaries, one persistent process

`engramux.exe` — console subsystem. Hook relay and CLI.
`engramux-service.exe` — GUI subsystem (`-H=windowsgui`). Started by Task Scheduler at user logon.

**Why two.** The PE Subsystem field takes one value per binary. **[verified]** A console-less
parent spawning a console child with default creation flags produces a real, visible console
window; `CREATE_NO_WINDOW` and `DETACHED_PROCESS` suppress it, but Task Scheduler controls the
service's own flags, not ours. So the service must itself be a GUI binary, and the relay must be a
console binary to inherit the host's stdio.

**Process count.** Persistent: exactly one, per user. Transient: one relay per hook event, alive
about 11 ms. **[verified]** Expected concurrent relays = event rate × lifetime: 0.003 at one
session, 0.023 at eight, **0.28 at a hundred**. Projects and sessions add no processes.

Cost: two build targets, two entry points, and a rule that the service passes `CREATE_NO_WINDOW`
to every child it spawns.

### 5.2 Named pipe, fixed name

Pipe name: the `engramux.v1` prefix followed by a hash of the user SID, under the local pipe
namespace.

**The name is fixed.** rev.2 appended a per-start random nonce to stop a same-SID squatter. That
is incoherent with §2's decision that a single SID is inside the trust boundary, and it breaks
I-09: thirty concurrent starts would mint thirty distinct names and all thirty would succeed. It
also forced a discovery file that was never specified. Removed.

**[verified]** The fixed name satisfies I-09: 20 rounds of 30 processes racing `ListenPipe` on one
name, synchronised on a shared start instant, produced exactly one winner every round, and every
loser got the same `Access is denied`. No mutex or lock file is needed.

DACL grants full control to SYSTEM and to the owning SID, with inheritance blocked.

Frame: 4-byte little-endian length, then UTF-8 JSON. The length is validated before allocation.
**The frame carries a request type** — `IngestEvent`, `Status`, `Doctor`, `Search`, `Drain` —
because I-08 routes every CLI read over this pipe.

### 5.3 Timeout budget

One coherent budget, replacing four unreconciled numbers in rev.3.

| Stage | Limit |
|---|---|
| Relay total wall clock | **1 s** |
| Dial | 200 ms |
| Post-dial (write, wait for ACK) | 800 ms |
| Service-side SQLite `busy_timeout` | 10 s |

Blowing any relay limit means spool and exit 0. **[verified]** Measured round trip is p50
**0.515 ms** / p95 **1.04 ms**, so 800 ms is 769× the p95. The service's budget is deliberately
larger than the relay's — the relay is not willing to wait for it.

rev.4 carried p50 11.3 ms / p95 14.2 ms here and lost the harness that produced them. The
re-measurement is 20× faster, and the discrepancy is explained rather than assumed away:
`go-winio` creates the next pipe instance only when `Accept` is called, and `tryDialPipe`
answers `ERROR_PIPE_BUSY` with an unconditional 10 ms sleep (v0.6.2 `pipe.go:229`). A
dial-while-busy benchmark measures that path at p50 10.30 ms, and 1,000 real round trips
contain no 10 ms outlier at all — so the old harness was paying one busy retry per iteration.
The operational consequence survives the correction: **two relays back to back cost the second
about 10 ms**, which the 200 ms dial budget absorbs 19 times over.

The relay treats an ACK as success only when the version matches, the status is `committed`, and
the returned ingest ID equals the one it sent. rev.2 unmarshalled the ACK without checking status,
so a `rejected` reply counted as success and the event was lost permanently.

### 5.4 SQLite: exclusive locking, one connection

DSN pragmas: `locking_mode(exclusive)`, `foreign_keys(1)`, `recursive_triggers(1)`,
`synchronous(2)`, `busy_timeout(10000)`, `journal_size_limit(67108864)`, `secure_delete(1)`, plus
`_journal_mode=wal` and `_txlock=immediate`.

`synchronous(2)` is FULL. 3 is EXTRA. rev.2 wrote 3 in six places and called it FULL.

**Why exclusive.** Two problems. `modernc.org/sqlite` is compiled with `SQLITE_OMIT_SEH=1`
**[verified]**, so it cannot convert a filter driver's fault on the `-shm` mapping into an error
code the way an MSVC build does — and in Go the consequence is worse than upstream's own
documentation describes, because the fault reaches the runtime at a mapped address, where it is
`throw("fault")`: fatal, and invisible to `recover`. `locking_mode=EXCLUSIVE` buys the rest: a
second connection gets `database is locked`, 92% of baseline write throughput, zero errors under a
writer + reader + 50 ms-`TRUNCATE` checkpoint load. **[verified]**

**Why `journal_mode` is not a `_pragma` value.** SQLite's own WAL documentation, §8: *"If EXCLUSIVE
locking mode is set prior to the first WAL-mode database access, then SQLite never attempts to call
any of the shared-memory methods and hence no shared-memory wal-index is ever created."* rev.4
rested the SEH argument on that sentence, marked it `[verified]`, and the DSN did not satisfy it.
`modernc.org/sqlite` sorts `_pragma` values lexicographically before applying them, so
`journal_mode(wal)` inside that list ran before `locking_mode(exclusive)` — j before l — and
`PRAGMA journal_mode` reads the schema, which opens the wal-index while the pager is still in
normal locking mode. A `Wal` opened that way cannot move to heap memory afterwards.

`_journal_mode` is applied after the whole `_pragma` list, so `locking_mode` is in force first, and
no `-shm` is created — not on reopen, not on write, not while recovering a hot WAL. **[verified]**
The two orderings are not equally well founded: the driver states its apply order in its exported
package documentation and tests it, while the `_pragma` sort is documented nowhere. This does not
generalise to shorthand keys as a class — `_busy_timeout` and `_auto_vacuum` are applied *before*
the `_pragma` list (§7.1).

**How the false claim survived four revisions, because that is the reusable part.** A database the
process itself creates has no `-shm` under either ordering, since there is no schema to read and no
WAL to open. That is the only case `docs/evidence/exclusive` ever measured, and every test written
after it measured the same one. Three states are now asserted separately, one test each: a
brand-new database, a reopen of it, and a reopen over the hot WAL a kill leaves. Only the second and
third can fail. Checkpointing changes none of them, on any schedule (§7.4-4).

Cost, and it is not small: one connection, no writer/reader pool split, and no process other than
the service can open the database — which is what forces I-08.

**Transactions.** `_txlock=immediate` plus ordinary `db.BeginTx` / `tx.Commit`. Raw `BEGIN IMMEDIATE`
SQL is banned: a single missed `ROLLBACK` wedges the one connection permanently.

**Pragma verification.** **[verified]** Only `_pragma` values skip DSN validation — `syncronous(3)`
returns `err=nil` and SQLite ignores it silently. Hence I-11. `_txlock` is the one DSN setting this
cannot check, since it is not a pragma, so its behavior is pinned by a test instead.

I-11's name check counts `_journal_mode=…` as naming `journal_mode`, and both halves still apply to
it. A **key** typo — `_journal_mdoe=wal` — is silent under either spelling: nothing reads the
parameter, SQLite is never told anything, and `journal_mode` reads back as whatever the file already
was, which for an existing database is `wal`. Only the name check catches that. A **value** typo is
the half that improves: `_journal_mode=wla` is refused by the driver's own enum validator before any
pragma runs, where `_pragma=journal_mode(wla)` would have been executed verbatim and ignored.
**[verified]**

**Checkpointing.** Straight `TRUNCATE`, on a timer and on a size threshold. rev.3 specified a
`PASSIVE` probe with conditional escalation, on the theory that a blind `TRUNCATE` could hold the
connection for the full 10 s `busy_timeout`. **[verified]** That theory was inherited from a design
with several connections and does not survive measurement: cold `TRUNCATE` costs about 0.54 ms per
MiB of WAL — 32.5 ms at the 64 MiB threshold — and reports `busy=0` every time, because under
exclusive locking there is no other connection to block on (§7.4). Threshold 64 MiB, the same number
as `journal_size_limit`; timer 5 minutes; the WAL size is read by stat every 5 seconds, so the
threshold is honoured to within 0.2% of itself at the busiest rate §7.2 measured. Plus one
`TRUNCATE` on the way out, which is the shutdown path that receives `os.Interrupt`.

**What checkpointing is and is not for.** The DSN above does not set `wal_autocheckpoint`, so
SQLite's default of 1,000 pages stands and SQLite `PASSIVE`-checkpoints on its own. **[verified]**
The WAL therefore settles at about 4.1 MiB — 4,124,152 B after 400 ingests and 4,128,272 B after
800, and 4,144,752 B on the live installation — rather than growing. §7.2's 12,439 B per event was
measured with `wal_autocheckpoint(0)` and does not describe this DSN. What the policy above adds is
the two things a `PASSIVE` checkpoint does not do: it gives the file back, since `PASSIVE` reuses
the WAL in place and leaves its high-water mark standing, and it bounds what a hard kill leaves for
the next start to recover. It does **not** keep the `-shm` away — the DSN does, and no checkpoint
schedule ever could.

The checkpoint on the way out is honest about its own worth: a clean `Close` already checkpoints
and removes the `-wal`, so removing that call changes no observable state and no test can tell.
**[verified]** It is kept because it states the shutdown rather than inheriting it from the driver.

### 5.5 Provisioning

Task Scheduler, user logon trigger, hidden, `MultipleInstancesPolicy=IgnoreNew`. Two settings the
XML must carry explicitly:

- `ExecutionTimeLimit` set to `PT0S`, which means run indefinitely. Microsoft documents the COM
  default as stopping a task 72 hours after it starts; the XML element is optional and documents no
  default for absence, so the behavior of omitting it is genuinely unresolved (§7.2). Writing it
  explicitly costs one line and removes the question.
- `RestartOnFailure` with a bounded count and interval.
- `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` both set to `false`. **[verified]**
  Both default to **true**, and on a laptop that is fatal to a logon-triggered service: the
  first refuses to start it while on battery, the second stops it the moment the cable comes
  out. Neither is mentioned by Microsoft's own defaults discussion because neither matters for
  the batch jobs Task Scheduler was built around; it matters for something that must be running
  whenever the user is.

`doctor` re-reads both from the registered task and reports them. Soak testing must exceed 72
hours, not equal it.

**Upgrade** is drain → stop → replace → start. The exclusive lock means the new service cannot open
the database until the old one lets go. Relays during the gap spool, which is the already-designed
path.

### 5.6 Filesystem layout

Under the user's local application data directory. Paths are a decision; formats are the code's.

| Path | Owner | Purpose |
|---|---|---|
| `engramux.db` (plus its WAL) | service | Everything |
| `spool/` | relay writes, service drains | Undelivered events |
| `health.json` | service | Panics, errors, spool depth, checkpoint results |
| `mcp.json` | service | Bound port and bearer token |
| `logs/` | service | Rotating logs |

`health.json` exists because `doctor` is a **separate process** and cannot read the service's
memory. rev.2's health tests passed a pointer within one process and proved nothing.

Every write is to a temporary file followed by an atomic rename.

The spool is bounded on file count, total bytes, and record age. A record that fails repeatedly is
quarantined rather than retried forever. Draining is a context-aware bounded batch, because it
competes with live ingest for the single connection.

### 5.7 Search targets raw event text

FTS5 over the **original string leaves of the event payload**, using external-content tables.

**Amendment — this line used to say "over the redacted event payload", and both halves of that were
wrong.** What is indexed is the *original* text, never a masked form, and it is not the payload: it
is every JSON string leaf of the payload, in document order, newline-joined, with object keys
skipped. Masking happens at egress and nowhere else. Three reasons, none of them a preference.
I-10 keeps the original in the database — a secret is tagged, never erased — so an index of masked
text would disagree with the table it is built over on every tagged row. External content makes
that fatal rather than untidy: `rebuild` reads the content table, so a masked index would be
silently replaced by the unmasked text the first time anything rebuilt it, and no check would say
so. And the user-identity class fires on **900 of 902** captures (§6.1), so a masked index would
make every path and every username unsearchable, which is a large part of what a person searches
for.

**[verified] — the leaves and not the raw JSON, decided by the gate's precision assertion.**
Indexing the payload bytes indexes the structure: `session`, `id`, `hook`, `event`, `name` and
`cwd` are tokens of 901 of 902 documents against 76–277 for text a person wrote. Measured with
`TestPhase4Gate` over one unchanged corpus, changing only what the index holds: a search for `cwd`
— a key, never content — matched **900 of 901** corpus documents against a bound of 103, of which
**797 carried it in no string leaf at all**, and **4 of 4** fixtures against a bound of 0. Over the
leaves index the same search matches **76 of 901** and **0 of 4**, with **no** hit that fails to
carry the word in a leaf. The bound is counted from the documents themselves rather than chosen,
and 76 is below 103 because the bound counts a substring of a leaf while the index matches a token.
The gate logs both figures on the passing path — *"corpus / precision: MATCH "cwd" returned 76
documents, bound 103"* — so the number here comes out of the committed harness rather than out of a
probe nobody kept.

Structure only ever raises recall, and the measurement says it was raising none here. Of the ten
recall runs, **six completed and returned the same found-of-sampled count as before** — the gate
reports a count and not an identity, so a count is what is claimed — and **four aborted on an FTS5
syntax error** in the derived query, before and after alike, so they measured nothing either way.
Two corpus rank statistics improved. The five classes stay red in both modes until per-token
expansion lands, which is what this section already says is required and what T5 adds.

| Fixtures, 4 documents | Raw payload | String leaves |
|---|---|---|
| two-character Korean | 0 of 3 | 0 of 3 |
| a content word carrying a particle | 1 of 3, rank 1 | 1 of 3, rank 1 |
| two tokens | FTS5 syntax error | FTS5 syntax error |
| camelCase | 0 of 3 | 0 of 3 |
| a path basename | FTS5 syntax error | FTS5 syntax error |
| precision, `cwd` | 4 matched, bound 0, 4 on structure — **fails** | 0 matched, bound 0, 0 on structure — **holds** |

| Corpus, 901 documents | Raw payload | String leaves |
|---|---|---|
| two-character Korean, 196 carry one | 2 of 25, rank median 9 | 2 of 25, rank median 9 |
| a content word carrying a particle, 162 | 5 of 25, rank median 11, worst 41 | 5 of 25, rank median 10, worst 37 |
| two tokens, 860 | FTS5 syntax error | FTS5 syntax error |
| camelCase, 144 | 5 of 25, rank median 17, worst 23 | 5 of 25, rank median 17, worst 23 |
| a path basename, 900 | FTS5 syntax error | FTS5 syntax error |
| precision, `cwd` | 900 matched, bound 103, 797 on structure — **fails** | 76 matched, bound 103, 0 on structure — **holds** |

The two walks that produce the column — Go's at ingest and the migration's `json_tree` backfill for
the rows that predate it — must agree, or the live installation's existing events are indexed
differently from every event after them and nothing else notices. `TestTheTwoWalksAgree` (§7.1) is
what holds them together.

**Why not extracted titles.** Without an LLM the deterministic extractor produces titles of the
form `<tool>: <basename>` — ASCII, and carrying almost none of what happened.

**[verified]** Raw events carry the content; titles do not. Korean appears in **228 of 902 captures
(25.3%) across 10 host×event cells**, and it arrives through the fields a title throws away:
`tool_input.command` (86), `tool_response.stdout` (68), `tool_input.content` (32),
`last_assistant_message` (28). `UserPromptSubmit` accounts for 9 of the 228. Reproduce: walk each
payload and record the JSON path of every string matching `[가-힣]`.

rev.4 originally asserted the opposite here — "Korean enters only through `UserPromptSubmit`, 19 of
901" — and marked it `[verified]`. It was never measured. The decision survives the correction and
is strengthened by it: a title index would be near-empty of the text people actually search for.
What the correction does invalidate is the claim that a Korean recall gate is unreachable. It is
reachable over raw events, so §8's Phase 4 gate needs a real target rather than an excuse.

Tokenizer: `porter unicode61 remove_diacritics 2`, **no prefix index**. Queries expand per token
with a trailing `*`.

**[verified] — the prefix index is dropped, and this is what it was priced at.**
`BenchmarkPrefixIndex` in `internal/search` builds both indexes over one set of rows and times ten
two-character Korean prefix queries derived from the corpus by the gate's own rule. p50 per query,
median of three runs:
**129 µs without the prefix index against 84 µs with it at 901 events, and 792 µs against 643 µs at
18,020** — the corpus ingested twenty times over, which is a few days of the live capture rate. The
prefix index is the faster and larger of the two throughout. It costs **2.70× the index at 901
and 2.79× at 18,020** (1,208,726 B → 3,266,985 B; 21,322,323 B → 59,537,587 B, `sum(length(block))`
over the `%_data` shadow table). So the clause buys about **0.15 ms** at the larger scale, three
orders of magnitude inside §5.3's 1 s budget, and charges another 38 MB on top of 21 MB for it.
It goes. A later migration plus a `rebuild` adds it back if a real workload ever wants it. The
"about 3.2×" this section used to carry was never measured on this corpus; on this one it is
2.7–2.8×.

Per-query figures are derived from batched samples, because Go's monotonic clock on Windows steps
in about a millisecond and a single 129 µs query timed alone reads zero more often than not. They
were taken while the table still carried the `project_id UNINDEXED` column removed below, and were
not re-run for it; the size figures were, and each index lost exactly **1 byte**, which is what that
column was worth.

**[verified] — one indexed column, the leaves, and no `project_id UNINDEXED` beside it.** A
project-scoped search joins `events` on the rowid and filters `events.project_id`. An `UNINDEXED`
column looked like it would push that filter inside the MATCH; on an external-content table it does
not, and `EXPLAIN QUERY PLAN` says so. Over 2,000 events, in the production `ORDER BY rank` shape,
`MATCH … AND project_id = ?` plans as `SCAN events_fts VIRTUAL TABLE INDEX 32:M2` — **identical to
the same MATCH with no filter at all**, so the constraint never reached the virtual table's index.
The join form plans as that same scan plus `SEARCH e USING INTEGER PRIMARY KEY (rowid=?)`, and an
index built without the column at all plans the same way, as `… INDEX 32:M1`. All three return the
same 286 rows. The column bought nothing and is gone.

Reading those plan strings: `32` is the idxNum, and it is `ORDER BY rank` — the same queries without
it plan as `INDEX 0:…`. The `M` and its digit are written by `fts5BestIndexMethod`, which emits `M`
for a MATCH and then the **column index** it applies to; a whole-table MATCH targets the hidden
table-name column, whose index is the column count, so it falls from 2 to 1 when `project_id` goes.
Neither digit ever records the `project_id` constraint, which is the finding.

FTS5's own `secure-delete` is set to 1 on the table. §5.4 already decided `secure_delete(1)` for the
database file, and the index holds the same unredacted text behind a separate switch — without it a
deleted row leaves recoverable index entries until an `optimize`. It makes the table unreadable by
FTS5 older than 3.42.0, which nothing here is.

**[unverified] — and the number this paragraph used to carry is withdrawn.** rev.4 said "on 12,664
real documents this configuration reaches 93.3% micro-averaged recall" and marked it `[verified]`.
`34b36cc` had already removed the matching §7.1 row, in its own words: *"Three [verified] rows had
no artifact in the repository: relay round trip, the 12,664-document FTS harness, and the mutation
log. Removed rather than demoted."* The claim survived here because nobody re-read §5.7 when §7.1
was cleaned. It is removed now.

Three things are wrong with it beyond the missing harness, and they are why no future measurement
should reuse its shape. A "document" was a `memory_items` row, and §5.8 leaves that table empty in
1.0 — nothing in this product's data reproduces 12,664 (events are 902; string leaves 14,852).
Micro-averaging was **banned by name** in two earlier revisions for hiding Korean failure behind
bulk English matching. And the metric was a `COUNT(*)` match, which rev.2 itself called "not a
search-quality metric".

What survives, and what §8's gate is rebuilt on:

- The **decisions** are sound and separately supported — raw event text over titles, external
  content over independent tables, per-token expansion over wrapping the whole input.
- **[verified]** A trigram tokenizer cannot match fewer than **3 characters in any script**. That
  is documented behaviour, not a Korean-specific finding, and it alone disqualifies it here.
- **[verified]** `prefix='2 3 4'` does **not** make a two-character query match. Only the trailing
  `*` does. This section read as though the prefix index bought recall; it buys latency, and the
  latency has now been measured and was not worth its size — see above.
- **[verified]** Per-token expansion must quote the token: `"token"*`, star outside the quotes.
  Bare `token*` is a **syntax error** on the shapes this corpus is full of — a hyphenated
  identifier answers `no such column: time`, and a Windows path answers `no such column: C`.
- **[verified]** `unicode61` does not split a Latin stem from an attached Korean particle:
  `Codex는` is one token. So an exact-word search for `Codex` misses it, which is what makes
  per-token expansion load-bearing rather than a convenience.

Measure the replacement once, with the harness committed beside the number this time.

**[verified]** `AFTER UPDATE` triggers on an external-content table are safe when old values are
passed explicitly. rev.1 proposed independent (non-external) tables; that makes `rebuild` silently
empty the index, leaves `'delete'` unsupported, and loses base rows to rowid reuse.

### 5.8 1.0 is pull-only

SessionStart injects nothing. Memory is retrieved on demand through MCP.

**Why.** Without an LLM the only thing available to inject is deterministic extraction, and §5.7
establishes what that is worth. Forcing it into every session costs tokens for no benefit. Push
injection turns on in 1.1, when there is something worth pushing.

Consequences: the Codex context-limit question is moot for 1.0. `observations` and `memory_items`
keep their schema slots, but 1.0 writes nothing to them and no gate depends on them.

### 5.9 MCP

Streamable HTTP on `127.0.0.1`, bearer token, cross-origin protection enabled. **[verified]** In
go-sdk v1.7.0 the `CrossOriginProtection` struct field is deprecated (`mcp/streamable.go:190`);
wrap the handler with the middleware instead. `MaxRequestBodyBytes` defaults to 4 MiB
**[verified]**. Localhost protection stays on.

I-13 is not weakened by the same-SID trust boundary. `127.0.0.1` limits the machine, not the
process.

## 6. Data model

Tables and their meaning. The DDL lives in the migration; the migration is the truth.

| Table | Holds | Notes |
|---|---|---|
| `projects` | Project identity | Identity means: same repository, same worktree. It must survive drive-letter case and trailing-separator differences. The hash inputs are the code's choice; the meaning is not |
| `sessions` | One row per host session | The id combines host and host session id. Status advances on `SessionEnd` and `Stop` |
| `events` | Every captured event | `id` is the relay-minted UUIDv7 and **is** the idempotency key (I-05). `tool_use_id` is a nullable, non-unique column used to pair `PreToolUse` with `PostToolUse`. `privacy_class` carries the secret tag (§6.1) |
| `observations` | Deterministic extraction | Schema present, unwritten in 1.0 (§5.8) |
| `memory_items` | Curated memory | Schema present, unwritten in 1.0 (§5.8) |
| `events_fts` | FTS5 external content over the string leaves of `events.payload` | §5.7. The leaves are a derived column on `events`, filled on the way in and backfilled by the migration for the rows that predate it |

Column domains that matter:

- `events.host` — `claude-code`, `codex`, `unknown`. `unknown` is reachable: I-04 stores an
  unclassifiable event rather than dropping it, because spooling cannot fix a payload that will
  never classify.
- `events.source` — `pipe` or `spool`. Set by the service from the ingest path, not carried in the
  envelope.

Field values are capped at **512 KiB** by a limiter that preserves JSON validity. A naive byte
truncation produces a payload that fails to marshal, and the relay then drops the event without
either sending or spooling it.

Foreign keys from `sessions`, `events`, `observations`, and `memory_items` to `projects` carry
`ON DELETE CASCADE`. Project purge is **not in 1.0** — the schema prepares for it, and `forget` and
`purge` are not exposed.

Writes to `memory_items` use `ON CONFLICT … DO UPDATE`. `INSERT OR REPLACE` is banned: it deletes
and reinserts, which fires cascades and loses the rowid.

### 6.1 What a secret is, and what happens to it

Erasing a secret from the database would destroy exactly the memory this product exists to keep —
"I put the key in `.env`" is useful context, and a row reading `[REDACTED]` is not. So the database
keeps the original and carries a tag. Every path out of the machine filters on that tag.

**Detection is deliberately generous.** Because a match tags rather than destroys, a false positive
costs nothing. A false negative is the only expensive outcome, so err toward tagging.

| Class | Shape |
|---|---|
| Provider API keys | `sk-ant-`, `sk-proj-`, `sk-`, `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `xox[baprs]-`, `AKIA` + 16 uppercase alphanumerics |
| Key material | Any `-----BEGIN … PRIVATE KEY-----` block |
| Authorization | `Authorization:` or `Bearer` followed by a token. The token pattern must be bounded as `[^\s"',}\]]+` — `\S+` swallows the closing quote and brace and produces JSON that no longer parses |
| Credential assignments | `password`, `passwd`, `secret`, `api_key`, `api-key`, `token` followed by `=` or `:` and a value |
| Connection strings | A URL with credentials in the authority, e.g. `scheme://user:pass@host` |
| `.env` content | Multi-line `NAME=value` blocks where the name is uppercase |
| Opaque runs | Base64 or hex runs of 40 characters or more |
| User identity | Absolute paths containing a Windows user directory. **[verified]** This is the one that actually fires: 1,714 matches across **900 of 902** captures, while every credential class above matches 4 files in total |

`privacy_class` records which classes matched. `redaction_version` records the ruleset that decided,
so a later ruleset can re-scan without ambiguity about what an old row was judged against.

**Egress filtering is the invariant, not detection.** A log line, a search result, an export, and a
synthesised fixture all pass through the same filter. A test that only checks "the detector found
something" does not test I-10; the test that does is one that puts a tagged row through each egress
and asserts the secret is absent from the output.

### 6.2 Fixtures are synthesised

Fixtures under `tests/fixtures/` copy the **shape** of real captures — JSON key paths, types,
nesting — and invent every value. No raw capture is ever committed.

**[verified]** This is not caution about hypotheticals. Real captures carry the user's work, not
just their username: Korean text alone appears in 228 of 902 captures through `tool_input.command`
(86), `tool_response.stdout` (68), `tool_input.content` (32), and `last_assistant_message` (28) —
that is real commands, real output, and real file contents. `origin` is public.

The cost of synthesis is drift: an invented fixture can stop matching what the host actually sends.
The guard is a **shape test** that reads `.capture/fixtures-raw/` locally and asserts every fixture's
key paths and types still occur in the real corpus. It is skipped when the corpus is absent, so
contributors can run everything else.

Synthetic secrets for the redaction break-it step are generated **at test runtime and never written
to the repository**. A committed `known-bad` file would put credential-shaped strings in a public
repository, which trips push protection and is indistinguishable from a real leak. The generator
itself needs a test: assert it produces a string the detector matches, so a generator that silently
emits something harmless cannot make the break-it step vacuous.

### 7.4 Decisions the re-measurement changed

1. **Peer verification does not need process creation time.** Zero PID reuse occurred inside the
   relay's 1 s budget. The rule instead is: verify the peer PID on the accepted connection and
   never cache it — at 48.93% overall reuse, a PID held past about a second means nothing.
2. **Checkpointing does not need a PASSIVE probe.** §5.4's escalation policy was inherited from a
   design with several connections. Cold `TRUNCATE` on an exclusive single connection is linear and
   cheap: 5.7 ms at 9.8 MiB, **32.5 ms at 66.1 MiB**, 140.5 ms at 258.3 MiB — roughly 0.54 ms/MiB,
   with `busy=0` every time. At the 64 MiB threshold that is 3% of the relay's entire budget. There
   is no other connection to block on.
3. **The 512 KiB field cap is not binding on real data.** Corpus payloads: p50 1,182 B, p90 7,418 B,
   p99 32,936 B, max 171,764 B. The cap is a guard against pathological input, not a routine path.
4. **Checkpointing has nothing to do with the `-shm`, and the reason the WAL is bounded is not
   checkpointing.** Both were assumed and both are wrong. The wal-index appeared on every reopen of
   an existing database whatever the WAL contained, so no schedule prevented it and the shutdown
   checkpoint could not either; what removed it was one DSN key (§5.4, §7.1). And the WAL was
   already bounded, by SQLite's own `wal_autocheckpoint`, which §5.4's DSN never disables. The
   checkpoint policy stays as specified —
   `TRUNCATE` is still the only thing that returns the file's space and still bounds crash recovery
   — but it is a reclamation policy, not the thing standing between the service and an unbounded
   file. §7.2's growth rate is what one checkpoint has to move; it is not the size the WAL reaches.

### 7.5 Corpus hygiene

The raw corpus is a local reference, not a source of committed files (§6.2). Two things about it
matter to anything that reads it:

- It contains one synthetic self-test payload (`session_id == "selftest"`) whose timestamp is the
  earliest in the Claude `PreToolUse` bucket. Anything that walks the corpus in timestamp order and
  takes the first match gets this one. Filter it.
- **[verified]** 900 of 902 captures contain an absolute path with the user directory in it. Nothing
  derived from the corpus leaves the machine without that being handled.

## 8. Phase gates

Every gate is marked `[auto]` (a test) or `[manual]` (an observation). A `[manual]` gate is a
condition for proceeding, not a test case.

Every `[auto]` gate guarding an invariant carries a break-it step: break the implementation
deliberately, confirm the test fails, revert. rev.2's suite survived 15 of 20 such breaks because
its assertions checked presence rather than value.

| Phase | Delivers | Gate |
|---|---|---|
| **1** | Capture → journal → ACK → replay for four fixtures, plus secret tagging and one egress filter | `[auto]` The four fixtures round-trip byte for byte; `foreign_key_check` returns empty; a kill between COMMIT and ACK replays exactly once; a runtime-generated secret is tagged on ingest and absent from the log |
| **2** | The remaining events, behind the 22-cell host×event allowlist, **default off** | `[auto]` Each cell's fixture passes before that cell is enabled, in the same commit. **[verified]** Only 13 of the 22 cells occur in the corpus; the other 9 need captures that only the user can produce, since an agent does not edit host configuration |
| **3** | Service, singleton, provisioning | `[auto]` 30 concurrent starts leave one service. `[manual]` `doctor` reports the execution time limit and restart policy |
| **4** | FTS5 and search | `[auto]` **Known-item retrieval, gated per class.** The query is derived from the document it must find, so relevance judgements are free and anyone can re-run it. Classes, each gated separately because an average hides exactly the failure that matters: two-character Korean, a content word carrying a particle, two tokens, camelCase, and a path basename. One precision assertion alongside, because a recall-only gate cannot see what indexing structure destroys. Runs over the fixtures always and `.capture/` when present. §5.7's old baseline is withdrawn and must not be reused |
| **5** | MCP, four tools | `[auto]` Bearer required; cross-origin rejected; bound to `127.0.0.1` only |
| **6** | Hardening and soak | `[auto]` Redaction audit finds nothing. `[manual]` Soak exceeds 72 hours |

Phase 1 depends on no other phase.

Its four fixtures are chosen to cover every detection path and every payload shape at once, so
that no later phase is the first to exercise one:

| Fixture | Covers |
|---|---|
| `codex SessionEnd` | Detection step 3 only — the `transcript_path` fallback. A two-step rule loses all 13 |
| `codex PostToolUse`, string `tool_response` | Detection step 2; the shape an object-assuming parser breaks on |
| `codex PostToolUse`, array `tool_response` | The third shape, which is easy to miss after handling the string |
| `claude-code PostToolUse`, object with `stderr` and `interrupted` | Detection step 1; the only shape with error keys, and present in just 241 of 310 |

Concurrency gates must respect §5.4: a second connection cannot be opened, so the test asserts that
the second connection is **refused**, not that two connections race. rev.3's amendment list asked
for a race and was wrong.
