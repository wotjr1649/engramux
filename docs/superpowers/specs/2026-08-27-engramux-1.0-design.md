**Scope: everything through 1.0.** `2026-08-30-engramux-memory-architecture.md` decides what comes

## 1. What we are building

A Windows-first service that captures Claude Code and Codex session hook events into SQLite and
serves them back through FTS5 and MCP. One service per Windows user multiplexes every concurrent
session across every project.

The differentiator is automatic hook capture. `engram` (Go, SQLite+FTS5) requires the agent to
call `mem_save` explicitly and is MCP-stdio only. `claude-mem-lite` captures hooks but has no
Windows support. `thedotmack/claude-mem` does both and breaks constantly on Windows.

**Full behavior parity with claude-mem is not a 1.0 goal**, and its architecture is never a model —
that is the part that fails on Windows. Adopting an individual compatible behavior later is fine when
a spec asks for it; migration and interoperability are legitimate goals beyond 1.0.

## 2. Scope decisions

| Decision | Value |
|---|---|
| Purpose | Personal daily driver *and* public OSS product |
| Hosts | Claude Code and Codex, both in 1.0 |
| Events | The 11-event intersection only (Claude has 31 ⊃ Codex 11, Codex-only 0) |
| claude-mem migration | **Not in 1.0.** Start with an empty database |
| LLM summarization | **Not in 1.0.** No `Generator` or `Embedder` interface either — an unused interface is a design commitment we have not earned |
| Trust boundary | A single Windows user SID is **inside** the boundary |
| Event ordering | Partial order. Wall-clock time is not an ordering key |
| Secrets | Detected and tagged at ingest, never erased from the database. Filtered at every egress (§6.1) |
| Fixtures | Synthesised. Shape copied from real captures, every value invented (§6.2) |
| Search target | **The raw event text**, not extracted titles (§5.7) |
| Context re-injection | **1.0 is pull-only.** SessionStart emits nothing (§5.8) |
| Process model | One persistent service; relays are per-event and transient (§5.1) |

## 3. Invariants

These must hold at every commit. A change that breaks one is a design change, not a bug fix.

| # | Invariant |
|---|---|
| **I-01** | Exactly one persistent process per Windows user. Sessions and projects are rows, not processes |
| **I-02** | No per-session process. The service spawns a child only where a decision in §5 says so, and every such child is created with the no-window flag |
| **I-03** | A hook never blocks its host. The relay exits 0 on every path, including panic |
| **I-04** | A captured event is never silently dropped. If it cannot be delivered it is spooled; if it cannot be classified it is stored as `unknown` |
| **I-05** | Every event carries an idempotency key minted at capture time and reused across every retry |
| **I-06** | Ordering is partial. Two events are ordered only when the ingest path establishes it |
| **I-07** | The service holds the database exclusively. No other process opens it — ever, including read-only |
| **I-08** | Every CLI read travels over the pipe. There is no read-only fallback (I-07 forbids one) |
| **I-09** | The singleton is enforced by `ListenPipe` exclusivity on a **fixed** pipe name, plus Task Scheduler's `IgnoreNew` |
| **I-10** | A secret is **tagged, not destroyed**, on the way into the database. It never leaves the machine untagged: every egress — log, search result, export, fixture — filters on the tag (§6.1) |
| **I-11** | Every pragma is read back at startup and compared against its expected value. A mismatch fails startup |
| **I-12** | Host detection reads the payload, never argv |
| **I-13** | MCP binds `127.0.0.1` and requires bearer authentication |
| **I-14** | An event whose host×event cell is not explicitly enabled is stored but not parsed |

## 4. Host contract

This section is not ours to decide. It records what the two hosts actually do.

### 4.1 The 11-event intersection

`SessionStart` · `SessionEnd` · `UserPromptSubmit` · `PreToolUse` · `PostToolUse` · `Stop` ·
`SubagentStart` · `SubagentStop` · `PreCompact` · `PostCompact` · `PermissionRequest`

Claude Code exposes 31 events; Codex exposes 11; the Codex set is a subset. 1.0 handles the
intersection and nothing else.

### 4.2 Invocation shape

Claude Code takes `command` plus an `args` array (exec form, no shell). Codex takes
`commandWindows` as a single string. Claude Code has no `commandWindows` key; a hook that only
sets it is never invoked.

### 4.3 Host detection

The relay is told nothing about which host launched it — argv is not trustworthy because the same
binary path appears in both hosts' configuration. Detection reads the payload:

1. `prompt_id` or `effort` present → Claude Code
2. `model` or `turn_id` present → Codex
3. Neither → fall back to the directory component of `transcript_path` (`.claude` vs `.codex`)

**[verified]** Across 901 real captures, steps 1–2 classify 887 and step 3 classifies 13. One
capture remains unclassifiable — a synthetic self-test payload with `session_id == "selftest"` and
no `transcript_path`, which §7.5 requires filtering. After that filter: **900/900**.

A two-step rule (dropping `transcript_path`) loses **all 13 Codex `SessionEnd` events**. rev.2
specified the two-step rule and called it exhaustive; it was not.

### 4.4 Payload shape differences

**[verified]** `tool_response` on `PostToolUse` has different types per host:

| Host | Type | Count | Error keys |
|---|---|---|---|
| Claude Code | object | 310/310 | `stderr` and `interrupted` present in **241/310** only |
| Codex | string | 24 | — |
| Codex | array | 15 | — |

Any parser that assumes an object is wrong for every Codex event and for 69 Claude events. An
error-classification rule written against `tool_response.interrupted` never fires on Codex.

Reproduce: iterate `.capture/fixtures-raw/*PostToolUse*.json` and tabulate the type of
`payload["tool_response"]`.

### 4.5 stdout contract

**[verified]** Empty stdout is accepted by all 11 events on both hosts, confirmed across 901
captures. Since 1.0 is pull-only (§5.8), the relay writes nothing on any event.

## 5. Architecture decisions

Each entry states the decision, why, and what it costs.

### 5.1 Two binaries, one persistent process

`engramux.exe` — console subsystem. Hook relay and CLI.
`engramux-service.exe` — GUI subsystem (`-H=windowsgui`). Started by Task Scheduler at user logon.

**Why two.** The PE Subsystem field takes one value per binary. **[verified]** A console-less
parent spawning a console child with default creation flags produces a real, visible console
window; `CREATE_NO_WINDOW` and `DETACHED_PROCESS` suppress it, but Task Scheduler controls the
service's own flags, not ours. So the service must itself be a GUI binary, and the relay must be a
console binary to inherit the host's stdio.

**Process count.** Persistent: exactly one, per user. Transient: one relay per hook event, alive
about 11 ms. **[verified]** Expected concurrent relays = event rate × lifetime: 0.003 at one
session, 0.023 at eight, **0.28 at a hundred**. Projects and sessions add no processes.

Cost: two build targets, two entry points, and a rule that the service passes `CREATE_NO_WINDOW`
to every child it spawns.

### 5.2 Named pipe, fixed name

Pipe name: the `engramux.v1` prefix followed by a hash of the user SID, under the local pipe
namespace.

**The name is fixed.** rev.2 appended a per-start random nonce to stop a same-SID squatter. That
is incoherent with §2's decision that a single SID is inside the trust boundary, and it breaks
I-09: thirty concurrent starts would mint thirty distinct names and all thirty would succeed. It
also forced a discovery file that was never specified. Removed.

**[verified]** The fixed name satisfies I-09: 20 rounds of 30 processes racing `ListenPipe` on one
name, synchronised on a shared start instant, produced exactly one winner every round, and every
loser got the same `Access is denied`. No mutex or lock file is needed.

DACL grants full control to SYSTEM and to the owning SID, with inheritance blocked.

Frame: 4-byte little-endian length, then UTF-8 JSON. The length is validated before allocation.
**The frame carries a request type** — `IngestEvent`, `Status`, `Doctor`, `Search`, `Drain`, and
Phase 5's `GetEvent` and `ListSessions` (§5.9) — because I-08 routes every CLI read over this pipe.
A type this build does not serve is answered with a rejected `Ack`, which every reply document's
own `Verify` refuses, so an unimplemented type cannot be mistaken for an empty answer.

### 5.3 Timeout budget

One coherent budget, replacing four unreconciled numbers in rev.3.

| Stage | Limit |
|---|---|
| Relay total wall clock | **1 s** |
| Dial | 200 ms |
| Post-dial (write, wait for ACK) | 800 ms |
| Service-side SQLite `busy_timeout` | 10 s |

Blowing any relay limit means spool and exit 0. **[verified]** Measured round trip is p50
**0.515 ms** / p95 **1.04 ms**, so 800 ms is 769× the p95. The service's budget is deliberately
larger than the relay's — the relay is not willing to wait for it.

rev.4 carried p50 11.3 ms / p95 14.2 ms here and lost the harness that produced them. The
re-measurement is 20× faster, and the discrepancy is explained rather than assumed away:
`go-winio` creates the next pipe instance only when `Accept` is called, and `tryDialPipe`
answers `ERROR_PIPE_BUSY` with an unconditional 10 ms sleep (v0.6.2 `pipe.go:229`). A
dial-while-busy benchmark measures that path at p50 10.30 ms, and 1,000 real round trips
contain no 10 ms outlier at all — so the old harness was paying one busy retry per iteration.
The operational consequence survives the correction: **two relays back to back cost the second
about 10 ms**, which the 200 ms dial budget absorbs 19 times over.

**The service's reply gets its own deadline, and that is a fix rather than a nicety.** One deadline
set before the request frame is read covers the read, the handler and the write. The handler is
deliberately *not* bounded by it — abandoning an ingest already in flight is worse than answering
late — so a handler that runs long leaves the reply write whatever is left, and can leave it
nothing. The write then fails with `i/o timeout` while the client sees the connection close with no
frame on it. **[verified]** That was observed twice on the installed service, with one human client
and no contention, and nothing reproduced it until the handler was made slow on purpose. What makes
it slow in production is the `status` handler itself: a `COUNT(*)` and a `GROUP BY` over the whole
events table, against a cold page cache. Warm, the same command answers in about 180 ms (§7.1). The
reply now takes a fresh deadline after the handler returns. It does not extend what a stalled client may
hold a connection for: a stalled client sends no request, so no handler runs and the second deadline
is never set.

The relay treats an ACK as success only when the version matches, the status is `committed`, and
the returned ingest ID equals the one it sent. rev.2 unmarshalled the ACK without checking status,
so a `rejected` reply counted as success and the event was lost permanently.

### 5.4 SQLite: exclusive locking, one connection

DSN pragmas: `locking_mode(exclusive)`, `foreign_keys(1)`, `recursive_triggers(1)`,
`synchronous(2)`, `busy_timeout(10000)`, `journal_size_limit(67108864)`, `secure_delete(1)`, plus
`_journal_mode=wal` and `_txlock=immediate`.

`synchronous(2)` is FULL. 3 is EXTRA. rev.2 wrote 3 in six places and called it FULL.

**Why exclusive.** Two problems. `modernc.org/sqlite` is compiled with `SQLITE_OMIT_SEH=1`
**[verified]**, so it cannot convert a filter driver's fault on the `-shm` mapping into an error
code the way an MSVC build does — and in Go the consequence is worse than upstream's own
documentation describes, because the fault reaches the runtime at a mapped address, where it is
`throw("fault")`: fatal, and invisible to `recover`. `locking_mode=EXCLUSIVE` buys the rest: a
second connection gets `database is locked`, 92% of baseline write throughput, zero errors under a
writer + reader + 50 ms-`TRUNCATE` checkpoint load. **[verified]**

**Why `journal_mode` is not a `_pragma` value.** SQLite's own WAL documentation, §8: *"If EXCLUSIVE
locking mode is set prior to the first WAL-mode database access, then SQLite never attempts to call
any of the shared-memory methods and hence no shared-memory wal-index is ever created."* rev.4
rested the SEH argument on that sentence, marked it `[verified]`, and the DSN did not satisfy it.
`modernc.org/sqlite` sorts `_pragma` values lexicographically before applying them, so
`journal_mode(wal)` inside that list ran before `locking_mode(exclusive)` — j before l — and
`PRAGMA journal_mode` reads the schema, which opens the wal-index while the pager is still in
normal locking mode. A `Wal` opened that way cannot move to heap memory afterwards.

`_journal_mode` is applied after the whole `_pragma` list, so `locking_mode` is in force first, and
no `-shm` is created — not on reopen, not on write, not while recovering a hot WAL. **[verified]**
The two orderings are not equally well founded: the driver states its apply order in its exported
package documentation and tests it, while the `_pragma` sort is documented nowhere. This does not
generalise to shorthand keys as a class — `_busy_timeout` and `_auto_vacuum` are applied *before*
the `_pragma` list (§7.1).

**How the false claim survived four revisions, because that is the reusable part.** A database the
process itself creates has no `-shm` under either ordering, since there is no schema to read and no
WAL to open. That is the only case `docs/evidence/exclusive` ever measured, and every test written
after it measured the same one. Three states are now asserted separately, one test each: a
brand-new database, a reopen of it, and a reopen over the hot WAL a kill leaves. Only the second and
third can fail. Checkpointing changes none of them, on any schedule (§7.4-4).

Cost, and it is not small: one connection, no writer/reader pool split, and no process other than
the service can open the database — which is what forces I-08.

**Transactions.** `_txlock=immediate` plus ordinary `db.BeginTx` / `tx.Commit`. Raw `BEGIN IMMEDIATE`
SQL is banned: a single missed `ROLLBACK` wedges the one connection permanently.

**Pragma verification.** **[verified]** Only `_pragma` values skip DSN validation — `syncronous(3)`
returns `err=nil` and SQLite ignores it silently. Hence I-11. `_txlock` is the one DSN setting this
cannot check, since it is not a pragma, so its behavior is pinned by a test instead.

I-11's name check counts `_journal_mode=…` as naming `journal_mode`, and both halves still apply to
it. A **key** typo — `_journal_mdoe=wal` — is silent under either spelling: nothing reads the
parameter, SQLite is never told anything, and `journal_mode` reads back as whatever the file already
was, which for an existing database is `wal`. Only the name check catches that. A **value** typo is
the half that improves: `_journal_mode=wla` is refused by the driver's own enum validator before any
pragma runs, where `_pragma=journal_mode(wla)` would have been executed verbatim and ignored.
**[verified]**

**Checkpointing.** Straight `TRUNCATE`, on a timer and on a size threshold. rev.3 specified a
`PASSIVE` probe with conditional escalation, on the theory that a blind `TRUNCATE` could hold the
connection for the full 10 s `busy_timeout`. **[verified]** That theory was inherited from a design
with several connections and does not survive measurement: cold `TRUNCATE` costs about 0.54 ms per
MiB of WAL — 32.5 ms at the 64 MiB threshold — and reports `busy=0` every time, because under
exclusive locking there is no other connection to block on (§7.4). Threshold 64 MiB, the same number
as `journal_size_limit`; timer 5 minutes; the WAL size is read by stat every 5 seconds, so the
threshold is honoured to within 0.2% of itself at the busiest rate §7.2 measured. Plus one
`TRUNCATE` on the way out, which is the shutdown path that receives `os.Interrupt`.

**What checkpointing is and is not for.** The DSN above does not set `wal_autocheckpoint`, so
SQLite's default of 1,000 pages stands and SQLite `PASSIVE`-checkpoints on its own. **[verified]**
The WAL therefore settles at about 4.1 MB — 4,124,152 B after 400 ingests and 4,128,272 B after
800, and 4,144,752 B on the live installation — rather than growing. §7.2's 12,439 B per event was
measured with `wal_autocheckpoint(0)` and does not describe this DSN. What the policy above adds is
the two things a `PASSIVE` checkpoint does not do: it gives the file back, since `PASSIVE` reuses
the WAL in place and leaves its high-water mark standing, and it bounds what a hard kill leaves for
the next start to recover. It does **not** keep the `-shm` away — the DSN does, and no checkpoint
schedule ever could.

The checkpoint on the way out is honest about its own worth: a clean `Close` already checkpoints
and removes the `-wal`, so removing that call changes no observable state and no test can tell.
**[verified]** It is kept because it states the shutdown rather than inheriting it from the driver.

### 5.5 Provisioning

Task Scheduler, user logon trigger, hidden, `MultipleInstancesPolicy=IgnoreNew`. Two settings the
XML must carry explicitly:

- `ExecutionTimeLimit` set to `PT0S`, which means run indefinitely. Microsoft documents the COM
  default as stopping a task 72 hours after it starts; the XML element is optional and documents no
  default for absence, so the behavior of omitting it is genuinely unresolved (§7.2). Writing it
  explicitly costs one line and removes the question.
- `RestartOnFailure` with a bounded count and interval.
- `DisallowStartIfOnBatteries` and `StopIfGoingOnBatteries` both set to `false`. **[verified]**
  Both default to **true**, and on a laptop that is fatal to a logon-triggered service: the
  first refuses to start it while on battery, the second stops it the moment the cable comes
  out. Neither is mentioned by Microsoft's own defaults discussion because neither matters for
  the batch jobs Task Scheduler was built around; it matters for something that must be running
  whenever the user is.

`doctor` re-reads both from the registered task and reports them. Soak testing must exceed 72
hours, not equal it.

**`doctor` is most needed at the moment it is most broken**, which decides what it reports when the
service is down — §10's first open question, closed here. It reports everything knowable *without*
the service: the scheduled task registration and its settings, the two binary paths, the spool
depth, and the last line of the log. It marks the service section unreachable rather than omitting
it, and it exits 1. A version that returned at the first failure would print nothing about the
registration exactly when somebody is running `doctor` to find out why nothing started.

Two things only the service can answer, so `doctor` asks it for them rather than looking itself
(I-07 leaves nothing else able to look), and reports the *comparison* rather than a string for a
person to eye:

- the live `events_fts` tokenizer against what the migration declares. goose does not checksum, and
  an applied migration edited in place leaves an index whose DDL and whose contents disagree with no
  check that says so.
- the real database path. It is the one place in this product where an unmasked path is right: a
  local diagnostic, printed to the terminal of the SID that owns the file (§5.9 moves it out of
  every other reply).

**Upgrade** is drain → stop → replace → start. The exclusive lock means the new service cannot open
the database until the old one lets go. Relays during the gap spool, which is the already-designed
path. Migrations run at the new service's first start, and `00002` is not free: over a real
installation it is about a second and roughly double the database file, once (§7.1).

### 5.6 Filesystem layout

Under the user's local application data directory. Paths are a decision; formats are the code's.

| Path | Owner | Purpose |
|---|---|---|
| `engramux.db` (plus its WAL) | service | Everything |
| `spool/` | relay writes, service drains | Undelivered events |
| `health.json` | service | Panics, errors, spool depth, checkpoint results |
| `mcp.json` | service | Bound port and bearer token |
| `logs/` | service | Rotating logs |

`health.json` exists because `doctor` is a **separate process** and cannot read the service's
memory. rev.2's health tests passed a pointer within one process and proved nothing.

Every write is to a temporary file followed by an atomic rename. **That rule is not confined to this
directory**: it covers every file this product writes on a user's behalf, the two host configurations
the installer edits included. A direct write leaves a truncated file when it fails, and an installer
that fully rewrites one host's configuration before it has finished parsing the other's leaves a
split state that only a timestamped backup recovers.

The spool is bounded on file count, total bytes, and record age. A record that fails repeatedly is
quarantined rather than retried forever. Draining is a context-aware bounded batch, because it
competes with live ingest for the single connection.

### 5.7 Search targets raw event text

FTS5 over the **original string leaves of the event payload**, using external-content tables.

**Amendment — this line used to say "over the redacted event payload", and both halves of that were
wrong.** What is indexed is the *original* text, never a masked form, and it is not the payload: it
is every JSON string leaf of the payload, in document order, newline-joined, with object keys
skipped. Masking happens at egress and nowhere else. Three reasons, none of them a preference.
I-10 keeps the original in the database — a secret is tagged, never erased — so an index of masked
text would disagree with the table it is built over on every tagged row. External content makes
that fatal rather than untidy: `rebuild` reads the content table, so a masked index would be
silently replaced by the unmasked text the first time anything rebuilt it, and no check would say
so. And the user-identity class fires on **900 of 902** captures (§6.1), so a masked index would
make every path and every username unsearchable, which is a large part of what a person searches
for.

**[verified] — the leaves and not the raw JSON, decided by the gate's precision assertion.**
Indexing the payload bytes indexes the structure: `session`, `id`, `hook`, `event`, `name` and
`cwd` are tokens of 901 of 902 documents against 76–277 for text a person wrote. Measured with
`TestPhase4Gate` over one unchanged corpus, changing only what the index holds: a search for `cwd`
— a key, never content — matched **900 of 901** corpus documents against a bound of 103, of which
**797 carried it in no string leaf at all**, and **4 of 4** fixtures against a bound of 0. Over the
leaves index the same search matches **76 of 901** and **0 of 4**, with **no** hit that fails to
carry the word in a leaf. The bound is counted from the documents themselves rather than chosen,
and 76 is below 103 because the bound counts a substring of a leaf while the index matches a token.
The gate logs both figures on the passing path — *"corpus / precision: MATCH "cwd" returned 76
documents, bound 103"* — so the number here comes out of the committed harness rather than out of a
probe nobody kept.

Structure only ever raises recall, and the measurement says it was raising none here. Of the ten
recall runs, **six completed and returned the same found-of-sampled count as before** — the gate
reports a count and not an identity, so a count is what is claimed — and **four aborted on an FTS5
syntax error** in the derived query, before and after alike, so they measured nothing either way.
Two corpus rank statistics improved. The five classes stay red in both modes until per-token
expansion lands, which is what this section already says is required and what T5 adds.

| Fixtures, 4 documents | Raw payload | String leaves |
|---|---|---|
| two-character Korean | 0 of 3 | 0 of 3 |
| a content word carrying a particle | 1 of 3, rank 1 | 1 of 3, rank 1 |
| two tokens | FTS5 syntax error | FTS5 syntax error |
| camelCase | 0 of 3 | 0 of 3 |
| a path basename | FTS5 syntax error | FTS5 syntax error |
| precision, `cwd` | 4 matched, bound 0, 4 on structure — **fails** | 0 matched, bound 0, 0 on structure — **holds** |

| Corpus, 901 documents | Raw payload | String leaves |
|---|---|---|
| two-character Korean, 196 carry one | 2 of 25, rank median 9 | 2 of 25, rank median 9 |
| a content word carrying a particle, 162 | 5 of 25, rank median 11, worst 41 | 5 of 25, rank median 10, worst 37 |
| two tokens, 860 | FTS5 syntax error | FTS5 syntax error |
| camelCase, 144 | 5 of 25, rank median 17, worst 23 | 5 of 25, rank median 17, worst 23 |
| a path basename, 900 | FTS5 syntax error | FTS5 syntax error |
| precision, `cwd` | 900 matched, bound 103, 797 on structure — **fails** | 76 matched, bound 103, 0 on structure — **holds** |

The two walks that produce the column — Go's at ingest and the migration's `json_tree` backfill for
the rows that predate it — must agree, or the live installation's existing events are indexed
differently from every event after them and nothing else notices. `TestTheTwoWalksAgree` (§7.1) is
what holds them together.

**Why not extracted titles.** Without an LLM the deterministic extractor produces titles of the
form `<tool>: <basename>` — ASCII, and carrying almost none of what happened.

**[verified]** Raw events carry the content; titles do not. Korean appears in **228 of 902 captures
(25.3%) across 10 host×event cells**, and it arrives through the fields a title throws away:
`tool_input.command` (86), `tool_response.stdout` (68), `tool_input.content` (32),
`last_assistant_message` (28). `UserPromptSubmit` accounts for 9 of the 228. Reproduce: walk each
payload and record the JSON path of every string matching `[가-힣]`.

rev.4 originally asserted the opposite here — "Korean enters only through `UserPromptSubmit`, 19 of
901" — and marked it `[verified]`. It was never measured. The decision survives the correction and
is strengthened by it: a title index would be near-empty of the text people actually search for.
What the correction does invalidate is the claim that a Korean recall gate is unreachable. It is
reachable over raw events, so §8's Phase 4 gate needs a real target rather than an excuse.

Tokenizer: `unicode61 remove_diacritics 2`, **no prefix index**. Queries expand per token
with a trailing `*`.

**[verified] — a prefix query anchors at a token start, and nothing reaches inside a token.** This
is the limit the trailing `*` does *not* lift, and §8's derivations are built on it: a run of text
is reachable only where unicode61 begins a token, so a two-character Korean query reaches a document
holding `단계별로` and cannot reach one holding `0단계가`, where the digit and the run are a single
token. unicode61's token characters are the Unicode letter and number categories **and private
use** — measured, not read off the documentation: a superscript two (U+00B2, category No) and a
roman numeral nine (U+2168, Nl) both join a following Hangul run into one token, and so does U+E000,
while a symbol, an underscore and a parenthesis all separate. `TestTheIndexAnchorsAPrefixAtATokenStart`
in `internal/search` pins both halves — the anchoring and the categories — against FTS5 itself.
Nd alone is the wrong rule and was the rule two predicates in the gate used until Phase 4.

**Population A `[verified once, no committed harness]`, Population B `[verified]` — porter is
dropped, and this is what it was priced at.** The marking is split because the two tables below are
in different states, and one of them moved. Every number in both was measured and observed. The
harness that produced the **vocabulary sweep** — Population A, the 16,949-term table — was a
throwaway and is deleted, and nothing in the tree walks `fts5vocab` under a stemmer, so no committed
check reproduces its `porter` column: treat those four numbers as measured once and undefended

The **known-item table** — Population B — no longer has that defect.

Every revision through Phase 4's second session named `porter unicode61 remove_diacritics 2` here,

**The decision is that porter's losses are structural and its gains are incidental, and the trade is
worth taking.** Stated plainly first, because the two tables measure different things and neither
alone settles it.

*Structural, on the losses.* Porter's rewrites are English suffix rules applied to whatever token
they are handed, and a token ending in Hangul matches none of them. Read back out of `fts5vocab`
under the stemmer: `replay를` indexes as `replay를`, unchanged, while the same word typed alone as a
query indexes as `replai` — so `"replay"*` does not reach it. The two halves of the index disagree
**by construction** on exactly the token shape a corpus that is a quarter Korean is full of. This is
suffix rules failing to fire and not an ASCII guard, which matters because there is no ASCII guard
to appeal to: `파일s` is rewritten to `파일` by the same pass. The camelCase column says the same
about identifiers in a corpus that is mostly code and shell. Those are systematic losses on the
product's main use case.

*Incidental, on the gains.* The 65,987 same-stem reaches are real and are **priced and accepted, not
shown to be absent** — the second table cannot see them, because every query in it is cut out of the
document it must find and is therefore reachable under a trailing `*` by construction. That
instrument can register porter's damage and can never register porter's benefit, so it is quoted
here for the damage only. What makes the gain incidental rather than load-bearing is that a user
recovers it by typing less: without the stemmer prefix sets nest, so shortening a query never loses
a document and someone who typed `corrections` and wants `corrected` can type `correct`. With the
stemmer that repair is itself unreliable — `"correcti"*` finds nothing where `"correct"*` finds it,
on the 297 of 16,949 surface forms whose stem is not a prefix of themselves. That is the measured
asymmetry, and it survives whichever population is weighted.

Two lesser points, marked as the weaker arguments they are. Nearly a third of the ad-hoc figure —
28,067 of 94,054 — is not inflection matching but a shortened query token widened by the star, which
in this corpus is as easily precision lost as recall bought; that reading is a judgement about
identifiers, not a measurement of them. And the sweep weights all 16,949 terms equally including
many nobody would plausibly type — **[unverified]**, since no query log exists to say which, so it
is recorded as a caveat on the sweep and not as a reason.

Costs recorded rather than argued away: the index grows from 981,642 to 1,025,897 bytes over the
same 901 documents (**+4.5%**) and from 15,157 to 16,949 distinct terms, and the 65,987 same-stem
reaches in the first table are genuinely given up.

What is and is not committed, precisely, because it is easy to overstate. **The vocabulary table's
`porter` column cannot be rebuilt from this tree**: nothing sweeps a term list under a stemmer. The
one committed reader of `fts5vocab` is `TestTheTokenizerReadsBothIllFormedShapesTheSameWay` in

`BenchmarkPrefixIndex`'s `alternateIndex` varies the prefix clause and never the tokenizer. Those
four numbers, and the 3,764 and 297 beneath them, rest entirely on the deleted harness. **The
known-item table is built rather than quoted.** `TestEveryCandidateDocumentIsReachable` takes the migration's own `CREATE`
statement out of `sqlite_schema` and substitutes two words — the table name and the tokenizer clause
— so the stemmed arm differs from the shipped index in the stemmer and in nothing else, not the
column, the content table or the prefix setting. It asserts the two columns differently, and
deliberately: the shipped one as a ratio, since a query cut out of a document must reach that
document whatever the corpus, and porter's per class against the numbers above, pinned only when the
run's candidate counts match this population — another corpus is a different table and pinning it to
these would assert something nobody measured. The `porter` total being below the `unicode61` total

What the sweep does not do is exercise the read path: it asks the index for the candidate's own
rowid and never builds a hit, so nothing in it is masked, ranked, limited or excerpted.
`TestPhase4Gate` remains that test, and keeps its 25-document sample of the shipped column running

The **decision** does not wait on that run and is not reopened. It rests on the ratio, not on the
byte counts: 0.15 ms against §5.3's 1 s budget, against something near 2.7× the index.

Per-query figures are derived from batched samples, because Go's monotonic clock on Windows steps
in about a millisecond and a single 129 µs query timed alone reads zero more often than not. They

**[verified] — one indexed column, the leaves, and no `project_id UNINDEXED` beside it.** A
project-scoped search joins `events` on the rowid and filters `events.project_id`. An `UNINDEXED`
column looked like it would push that filter inside the MATCH; on an external-content table it does
not, and `EXPLAIN QUERY PLAN` says so. Over 2,000 events, in the production `ORDER BY rank` shape,
`MATCH … AND project_id = ?` plans as `SCAN events_fts VIRTUAL TABLE INDEX 32:M2` — **identical to
the same MATCH with no filter at all**, so the constraint never reached the virtual table's index.
The join form plans as that same scan plus `SEARCH e USING INTEGER PRIMARY KEY (rowid=?)`, and an
index built without the column at all plans the same way, as `… INDEX 32:M1`. All three return the
same 286 rows. The column bought nothing and is gone.

**[verified] — what the project filter costs, and the decision that follows.** §5.9 scopes search to
one project, and the worry it had to answer is that a small project's `LIMIT` makes SQLite walk a
long ranked list to fill it. Measured on 19,503 synthetic events across 40 projects, `LIMIT 20`,
where one project holds 500 matches and one holds 3:

| Query | Unscoped | Scoped to the large project | Scoped to the 3-event project |
|---|---|---|---|
| A term in **every** document | 24.2 ms, 20 hits | 26.4 ms, 20 hits | **39.0 ms**, 3 hits |
| A term in **one document in a hundred** | 1.08 ms, 20 hits | 0.64 ms, 5 hits | 0.47 ms, 1 hit |

**The cost is set by the size of the match set, not by the filter**, and the reason is a fact the
worry did not have: `ORDER BY rank` makes FTS5 score **every** matching document before it returns
the first row, so the `LIMIT` never stops the scan early — for the unscoped query either. The worst
case is therefore +14.8 ms, +61%, on a query that already cost 24.2 ms *because it matched all
19,503 documents*, which is not a query a person types. At a realistic selectivity the scoped query
is **faster** than the unscoped one, because §5.7's phase two builds an excerpt per hit and a scoped
search returns fewer hits.

**Decision: no index, no second query shape, no deferral.** The filter is `AND events.project_id = ?`
on the joined row and stays that. `BenchmarkProjectScope` in `internal/search` is the reproduction,
and the plan it prints is the one this section already records:
`SCAN events_fts VIRTUAL TABLE INDEX 32:M1` plus `SEARCH events USING INTEGER PRIMARY KEY (rowid=?)`.

Reading those plan strings: `32` is the idxNum, and it is `ORDER BY rank` — the same queries without
it plan as `INDEX 0:…`. The `M` and its digit are written by `fts5BestIndexMethod`, which emits `M`
for a MATCH and then the **column index** it applies to; a whole-table MATCH targets the hidden
table-name column, whose index is the column count, so it falls from 2 to 1 when `project_id` goes.
Neither digit ever records the `project_id` constraint, which is the finding.

FTS5's own `secure-delete` is set to 1 on the table. §5.4 already decided `secure_delete(1)` for the
database file, and the index holds the same unredacted text behind a separate switch — without it a
deleted row leaves recoverable index entries until an `optimize`. It makes the table unreadable by
FTS5 older than 3.42.0, which nothing here is.

real documents this configuration reaches 93.3% micro-averaged recall" and marked it `[verified]`.
`34b36cc` had already removed the matching §7.1 row, in its own words: *"Three [verified] rows had

Three things are wrong with it beyond the missing harness, and they are why no future measurement

What survives, and what §8's gate is rebuilt on:

- The **decisions** are sound and separately supported — raw event text over titles, external

- **[verified]** A trigram tokenizer cannot match fewer than **3 characters in any script**. That

- **[verified]** `prefix='2 3 4'` does **not** make a two-character query match. Only the trailing

- **[verified]** Per-token expansion must quote the token: `"token"*`, star outside the quotes.

### 5.8 1.0 is pull-only

SessionStart injects nothing. Memory is retrieved on demand through MCP.

**Why.** Without an LLM the only thing available to inject is deterministic extraction, and §5.7
establishes what that is worth. Forcing it into every session costs tokens for no benefit. Push

Consequences: the Codex context-limit question is moot for 1.0. `observations` and `memory_items`

### 5.9 MCP

Streamable HTTP on `127.0.0.1`, with a static bearer token. stdio and Streamable HTTP are the only
transports MCP revision `2026-07-28` binds; the old HTTP+SSE transport is no longer one.

**[verified] the server does not currently offer that revision, and this section reasons from it in
two places.** Measured over `server/discover`, which is what a `2026-07-28` client sends:
`supportedVersions` is `["2025-11-25","2025-06-18","2025-03-26","2024-11-05"]`. An `initialize`
handshake cannot show this — SEP-2575 made `initialize` the legacy path and the SDK caps it at
`2025-11-25` however the server is configured, which is why the Phase 5 gate's own initialize probe
never caught it. The cause is `mcp.NewStreamableHTTPHandler` being given nil options, leaving
`StreamableHTTPOptions.Stateless` false; with only that field flipped on a bare SDK server the list
gains `"2026-07-28"` at its head and changes in no other way. What rests on the revision is the
transport sentence above and the authorization argument below, and neither is *wrong* under
`2025-11-25` — but both are currently arguments about a revision this server does not speak, which is
a different claim from the one they make. `TestTheServerOffersTheRevisionsItActuallyOffers` in
`internal/mcpserver` pins the measured list and fails when the field is set; backlog 30 carries the
change, which is a rebuild.

**Why not a stdio proxy over the existing pipe.** The cheaper-looking design is a stdio MCP server
the host spawns, relaying to the named pipe: no port, no token, no listener, and the pipe's DACL
back as the access control. Two independent reviews recommended it. It is rejected on one
measurement neither had. **[verified]**, on the installed binaries: opening `engramux.exe` for write
succeeds, and opening `engramux-service.exe` for write fails with `EBUSY`, errno `-4082` — Windows
holds an image lock on a running executable. The relay binary is writable today *because* a relay is
spawned per event and exits (§5.1). A stdio proxy is the opposite shape, one long-lived process per
host session, so it would hold that lock for as long as any Claude Code or Codex window is open.
§5.5's upgrade path would then require closing every host window rather than stopping one service,
and the installer's refusal path would fire on the relay carrying advice (`schtasks /end`) that
cannot apply to a host-spawned process. HTTP keeps the long-lived process inside the service, which
is the one binary the upgrade path already stops.

**The service binds the port, mints the token, and writes `mcp.json`.** §5.6 assigns that file to
the service and the assignment stands, including its temporary-file-plus-atomic-rename rule. The
installer *reads* it and never writes it. Giving either value to the installer — which an earlier
draft of this section did — buys a probe/bind race (an installer choosing a port before anything
binds it), a token the service does not hold, and rotation drift with no owner.

**I-13 is a machine boundary, not a SID boundary, and this is the cost the design accepts.** A
previous revision of this section said *"I-13 is not weakened by the same-SID trust boundary"*. That
sentence was false and is withdrawn. Binding `127.0.0.1` restricts which interface accepts a
connection and says nothing about which principal opens one: any process of any locally logged-on
user can reach the endpoint, and **the bearer token is the only control**. Windows offers no Winsock
equivalent of the named pipe's DACL, and `SO_EXCLUSIVEADDRUSE` prevents a second process stealing
the port rather than governing who connects. §2's trust boundary is one SID; every other ingress in
this product holds it structurally and this one does not. What follows: the token is a §6.1 secret,
minted once and then reused, and it is never logged, never printed by a CLI command, and never carried
in an error message. **[verified]:** what file permissions `mcp.json` carries once written. It
carries none of its own. Every ACE on it is inherited, Go's `0o600` writes nothing to the DACL, and
`os.Stat` reads the mode back as `0666` (§7.1). So the assumption this section told the reader to
make is the measured answer: **the bearer token is the whole of the control**, and the file's own
permissions add nothing to it. On the machine measured they subtract — the local application data
directory it inherits from grants a machine-local group read, so a second principal can read the
token — which is the same class of exposure the paragraph above already accepts rather than a new
one. Narrowing the DACL explicitly is a change of its own, with an atomic-write path to rework and
a security descriptor to build, and it is a backlog row rather than this phase's work.

**The port is bound, not derived, and the reason is a measurement.** **[verified] on this machine:**
`netsh int ipv4 show dynamicport tcp` reports start port 1024 and 13977 ports — an ephemeral range
of **1024 to 15000**, not Windows' documented default of 49152 to 65535. Excluded ranges are empty
at the time of measurement, and Hyper-V, WSL2 and Docker each reserve blocks the moment they start.
The general advice to put a fixed server port in the registered range 1024–49151 is therefore
**backwards here**: that is exactly where this machine's ephemeral allocator lives. **[unverified]:**
what any other machine's range is; what rests on it is any port derivation, so there is none. The
service binds port 0, lets Windows choose, and publishes the result in `mcp.json`. The port is
*sticky*: a start reuses the port the previous start recorded and falls back to 0 when that bind
fails, so a host configuration holding the URL stays correct across an ordinary restart. Bind is its
own probe, so no race exists. When the sticky port is lost, the URL in a host configuration is stale
until the installer is re-run, and `doctor` reports the disagreement. `netsh int ipv4 add
excludedportrange` would reserve a block and is a host-global network configuration change the
service does not make.

**The token is sticky for the same reason, and a previous revision of this section had it wrong.**
It said the token is *"minted per service start"*, and that sentence shipped. It made the product
break at every logon: the service is a logon-triggered task, so each logon minted a new token while
both host configurations still carried the previous one, every tool call answered 401, and `doctor`
reported it healthy because the sticky port kept the URL correct and the URL is all it compares.
Rotation bought nothing it was there for — the token's whole life is as a static header inside two
host configuration files where nothing rotates it, so rotating the service's copy shortens no
exposure window and only stops the two ends matching. What it cost is a credential that is invalid
more often than it is valid. So the previous start's token is reused, and one is minted only when
there is none to reuse or the one on disk is not a shape this product writes. The reused value is
checked against that shape first, because an empty token would make a bare `Authorization: Bearer `
header compare equal to every unauthenticated request. Rotation is the file: delete `mcp.json`,
restart, re-run the installer. **The reader lives in `internal/mcpserver`, not in the package
`doctor` imports**, which is what keeps §6.1's "never printed by a CLI command" structural rather
than editorial — the relay binary does not link the MCP SDK, so it cannot reach a token by any
route.

**The four tools** — this closes §10's question 3.

| Tool | Answers | Bounded by |
|---|---|---|
| `search` | §5.7's search over raw event text, scoped to one project | 100 hits, excerpt 240 runes, event name 64 runes |
| `get_event` | One event's whole payload, masked | A measured byte cap, below |
| `list_sessions` | The sessions of one project, newest first | A limit with a default and a cap, the same shape `search` has; `projects.root` masked |
| `status` | The numbers §5.2's `Status` request answers, masked | Nothing new, and **on this surface nothing at all**. The cell breakdown grows with distinct host×event pairs, and over the pipe `ipc.MaxFrameLen` is its ceiling; an MCP reply marshals straight to an HTTP response and never reaches `WriteFrame`, so the two surfaces do not fail alike. Real traffic is §4.1's 11 events across two hosts. A cap here needs a measurement nobody has, and an unmeasured cap is what `AGENTS.md` forbids — `list_sessions` and `SearchHit.EventName` carry the same asymmetry |

The project argument is **required in the MCP tool schema**, where the SDK enforces it structurally.
It is *optional on the wire*, where empty means all projects: §5.2's request set carries one meaning
per field, and an existing CLI invocation must not change what it returns. Those are two different
surfaces stating one rule at the level each can enforce it.

`get_event` takes an id **and** a project and checks them together. `events.id` is a relay-minted
UUIDv7 (I-05) and is unique across the whole database, so an id alone reads across projects.

**Every MCP reply is an I-10 egress and the reader is not a person.** The status reply leaves
`DatabasePath` unmasked on three grounds — one SID inside the boundary, the pipe's DACL admitting
only that SID, and a CLI printing it on the same machine. All three are void when the reader is a
model that may repeat what it read into a transcript that leaves the machine. So there is **one
masked status shape**, and the CLI sees the masked path too; a real path belongs in `doctor`, which
is a local diagnostic and not a tool. `SearchHit.EventName` is masked for the same reason — the spec
previously recorded it as a known I-10 perimeter, and Phase 5 closes it. `list_sessions` masks
`projects.root`, which is the exact shape `ClassUserPath` matches in 900 of 902 captures.

**`get_event` is bounded at 1 MiB, and the number is measured.** Every other egress here is bounded
— the excerpt to 240 runes, the event name to 64, the search reply to 100 hits — and a whole payload
would be the first that is not. The measurement is load-bearing because masking *expands*:
`secret.Mask` re-marshals whenever anything matched and `encoding/json` HTML-escapes, so one source
byte can become six, and the user-path class matches essentially every real payload, so the
re-encode path is the normal one and not the exception. **[verified]**, over the corpus: the largest
masked payload is **173,609 B** and the worst expansion is **1.1220×** (§7.1). 1 MiB is 6.0× that
largest and a quarter of `ipc.MaxFrameLen`, which leaves the rest of the reply three quarters of the
frame. §6's 512 KiB field cap used to be the other half of this sentence; it is withdrawn, and the
comparison that remains is the one that means something — 1 MiB against the largest masked payload
real traffic has produced.

Over the bound the payload is **left out, not cut**. A cut JSON document does not parse, and one
that parses and is short is worse — it looks whole. The reply still carries the event and the masked
byte count, so "too large" is distinguishable from "no such event", which returns no event at all.
Masked payloads are still valid JSON in 901 of 901 captures, which is what lets the reply splice one
in verbatim instead of escaping it into a string and roughly doubling it.

**Project scoping is a filtering-correctness property, not a security boundary.** §2 puts the whole
SID inside the trust boundary and the caller names the project, so no authorization check exists
here and none is implied by the word "isolation". The filter is post-MATCH and pre-LIMIT on
`events.project_id`: §5.7 measured that an `UNINDEXED` column buys nothing under external content,
so there is nothing to push inside the MATCH. **[verified]** — it is measured and it is not the
problem it looked like. §5.7 carries the figures and the decision: the cost is set by the size of
the match set rather than by the filter, because `ORDER BY rank` scores every matching document
before the first row is returned, so the `LIMIT` stops nothing early for the unscoped query either.
Worst case +61% on a query that matched every document in the database; at a realistic selectivity
a scoped search is *faster* than an unscoped one. No index, no second query shape.

**On the wire the project is optional and empty means every project; in the MCP tool schema it is
required.** One field with one meaning keeps a frame readable and keeps every existing CLI
invocation returning what it always returned. The requirement belongs where it can be enforced
structurally, which is the tool schema, because a model has no working directory to mean. The CLI
keeps its global default and gains `--project <path>`, read in first position only; there is no
`--all`, since that would be a flag for the default.

**A caller-supplied project path is a filesystem operation.** `project.Identify` stats every ancestor
up to the volume root and takes no context, so nothing can bound or cancel it, and §5.4's single
connection means a stall there stalls the whole service — a down UNC host or a vanished mapped drive
is the shape that does it. Absolute paths only, UNC rejected, walk depth bounded.

**The single connection needs three mechanisms, and `busy_timeout` is none of them.** MCP is the
first non-human caller of §5.4's one connection. `busy_timeout` governs SQLite lock contention and
§5.4 leaves no second connection to contend with; what actually waits is `database/sql` pool
acquisition, which `busy_timeout` does not touch, and the pipe handler receives the service's root
context rather than the client's deadline. So Phase 5 adds three things, verified separately:

- a **query deadline** on every read, so one query cannot hold the connection indefinitely. It is
  sized against the **client's** budget and not against the pipe's connection deadline, and the
  difference is a defect that reached the installed service: at the connection deadline's 2 s, the
  first `engramux status` after an idle period was **refused** with
  `group events by cell: context deadline exceeded` against a 108 MB database, while the same
  command warm takes 164–499 ms. The two scans a status runs are ~0.5 ms and ~8 ms warm at 12,000
  events, so what spends the budget is the page-cache I/O of reading the file. A deadline shorter
  than a legitimate cold read turns a working command into a refusal;
- a **read concurrency of one**, so queued reads do not multiply the wait;
- **ingest priority**: a waiting ingest goes before a queued read. I-04 is why this product exists,
  and a reader must not push a writer out.

The number they are held to is §5.3's: a reader holding the connection does not push a relay past
its 800 ms post-dial budget while an ingest is waiting. **That is measured warm.** A *cold* read of
a large database holds the connection for its whole statement and can exceed the relay's entire
budget on its own; the deadline bounds the wait and not the work, and what would bound the work is
an index `events` does not have — a migration, and a decision of its own. A relay that blows it spools and loses
nothing (I-04), which is why this is a budget and not a correctness clause — but a search that
quietly slows ingest is not a trade this design makes silently. **[verified]**: 20 ingests against
96 concurrent searches over 4,000 events land at a median of **1.5 ms** and a worst of **6.6 ms**;
without the gate the same load gives a median of **722 ms** and a worst of **2.66 s** (§7.1).

Two things about that are worth writing down rather than leaving to be rediscovered. **Priority is
worth less than it looks once concurrency is one** — `database/sql` already serves waiting
acquisitions in arrival order, so an ingest that queued first is served first either way; what the
rule adds is that it is *this design's* and is stated, rather than resting on a queue order the
standard library documents nowhere. And **the contention clause passes on read concurrency alone**,
which is exactly why each mechanism has a test of its own and why the wiring — the ingest handler
marking itself pending — needed a fourth test after a deliberate break found nothing holding it.

**The SDK, verified at `github.com/modelcontextprotocol/go-sdk` v1.7.0** (released 2026-07-28,
current, v1.x stable). `mcp.NewStreamableHTTPHandler` is the entry point.
`StreamableHTTPOptions.CrossOriginProtection` is **deprecated** in favour of wrapping the handler in
cross-origin middleware, and **it is nil by default, and nil means no protection is applied** — a
previous revision of this section said "cross-origin protection enabled", which does not describe a
default and is corrected here. The compatibility shim that restored the old default-on behavior is
telegraphed for removal in v1.8.0. `DisableLocalhostProtection` is a separate, live field defaulting
to false, so DNS-rebinding protection **is** on by default. `MaxRequestBodyBytes` defaults to 4 MiB.
`Stateless` defaults to false, which keeps a session map alive for the life of a process Phase 6
requires to soak past 72 hours. The cost was written here as "eight direct and three indirect
modules", which is the SDK's **own** `go.mod` and not what importing its `mcp` package adds to this
repository. **[verified]:** six new indirect modules — `google/jsonschema-go`, `segmentio/asm`,
`segmentio/encoding`, `yosida95/uritemplate/v3`, `golang.org/x/oauth2` and `golang.org/x/time` —
because `golang.org/x/sync` and `x/sys` were already here and `golang-jwt/jwt/v5`, `google/go-cmp`
and `golang.org/x/tools` are not reached from `mcp`. What it costs in linked bytes is §7.1's, and it
is the number to watch rather than the module count. Its `go` directive is 1.25.0, under
this repository's 1.26.0 ceiling. It marshals with `segmentio/encoding/json`, compared against
`encoding/json` on the two behaviours §7.1 pins — `RawMessage` compaction and HTML escaping — and
found byte-identical. None of it requires cgo.

**The two hosts, from primary sources, and both now smoke-tested.** Codex CLI `rust-v0.151.0`: an HTTP
server entry uses `url` where a stdio one uses `command`, with no separate transport key, and
`http_headers` is a documented map of static headers that OpenAI's own configuration reference names

a **different field** and is rejected; that is `openai/codex` issue 19275 against 0.124.0, closed

`experimental_use_rmcp_client` exists nowhere in the current source and was retired in January 2026;

about this product: it is true of those two versions, and it is the row to re-run on a host upgrade.

**A static bearer is spec-legal.** MCP revision `2026-07-28` makes authorization OPTIONAL and binds
only implementations that opt into its OAuth 2.1 framework. The condition is that the server does
not half-claim conformance: it must not advertise a `WWW-Authenticate` challenge naming
protected-resource metadata it does not serve.

## 6. Data model

Tables and their meaning. The DDL lives in the migration; the migration is the truth.

| Table | Holds | Notes |
|---|---|---|
| `projects` | Project identity | Identity means: same repository, same worktree. It must survive drive-letter case and trailing-separator differences. The hash inputs are the code's choice; the meaning is not |
| `sessions` | One row per host session | The id combines host and host session id. Status advances on `SessionEnd` and `Stop` |
| `events` | Every captured event | `id` is the relay-minted UUIDv7 and **is** the idempotency key (I-05). `tool_use_id` is a nullable, non-unique column used to pair `PreToolUse` with `PostToolUse`. `privacy_class` carries the secret tag (§6.1) |
| `observations` | Deterministic extraction | Schema present, unwritten in 1.0 (§5.8) |
| `memory_items` | Curated memory | Schema present, unwritten in 1.0 (§5.8) |
| `events_fts` | FTS5 external content over the string leaves of `events.payload` | §5.7. The leaves are a derived column on `events`, filled on the way in and backfilled by the migration for the rows that predate it |

Column domains that matter:

- `events.host` — `claude-code`, `codex`, `unknown`. `unknown` is reachable: I-04 stores an
  unclassifiable event rather than dropping it, because spooling cannot fix a payload that will
  never classify.
- `events.source` — `pipe` or `spool`. Set by the service from the ingest path, not carried in the
  envelope.

**There is no per-field size cap.** Earlier revisions specified one at 512 KiB, enforced by a
limiter that preserves JSON validity; it was never implemented, and the claim is withdrawn rather
than left standing over a tree that does not do it (backlog 24). What bounds a stored payload is
`ipc.MaxFrameLen`, which bounds the whole envelope, and nothing bounds one field inside it.

Withdrawn rather than implemented, because §7.4 measured the cap as not binding on real data — p99
**32,936 B**, largest **171,764 B**, against a 512 KiB cap — so implementing it would add a code
path real traffic never reaches, and the reason it was specified was to keep a naive byte truncation
from producing a payload that fails to marshal. Nothing truncates a field today, so there is no such
truncation to make safe. If a field cap is ever wanted, it is a design change with its own
measurement, and it has to be decided against masking's expansion (§5.9) and `get_event`'s 1 MiB
bound rather than beside them.

Foreign keys from `sessions`, `events`, `observations`, and `memory_items` to `projects` carry
`ON DELETE CASCADE`. Project purge is **not in 1.0** — the schema prepares for it, and `forget` and
`purge` are not exposed.

Writes to `memory_items` use `ON CONFLICT … DO UPDATE`. `INSERT OR REPLACE` is banned: it deletes
and reinserts, which fires cascades and loses the rowid.

### 6.1 What a secret is, and what happens to it

Erasing a secret from the database would destroy exactly the memory this product exists to keep —
"I put the key in `.env`" is useful context, and a row reading `[REDACTED]` is not. So the database
keeps the original and carries a tag. Every path out of the machine filters on that tag.

**Detection is deliberately generous.** Because a match tags rather than destroys, a false positive
costs nothing. A false negative is the only expensive outcome, so err toward tagging.

| Class | Shape |
|---|---|
| Provider API keys | `sk-ant-`, `sk-proj-`, `sk-`, `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `xox[baprs]-`, `AKIA` + 16 uppercase alphanumerics |
| Key material | Any `-----BEGIN … PRIVATE KEY-----` block |
| Authorization | `Authorization:` or `Bearer` followed by a token. The token pattern must be bounded as `[^\s"',}\]]+` — `\S+` swallows the closing quote and brace and produces JSON that no longer parses |
| Credential assignments | `password`, `passwd`, `secret`, `api_key`, `api-key`, `token` followed by `=` or `:` and a value |
| Connection strings | A URL with credentials in the authority, e.g. `scheme://user:pass@host` |
| `.env` content | Multi-line `NAME=value` blocks where the name is uppercase |
| Opaque runs | Base64 or hex runs of 40 characters or more |
| User identity | Absolute paths containing a Windows user directory. **[verified]** This is the one that actually fires: 1,714 matches across **900 of 902** captures, while every credential class above matches 4 files in total |

`privacy_class` records which classes matched. `redaction_version` records the ruleset that decided,
so a later ruleset can re-scan without ambiguity about what an old row was judged against.

**Egress filtering is the invariant, not detection.** A log line, a search result, an export, and a
synthesised fixture all pass through the same filter. A test that only checks "the detector found
something" does not test I-10; the test that does is one that puts a tagged row through each egress
and asserts the secret is absent from the output.

**`event_name` is a known perimeter of that "every".** A search hit's and a status cell's event name
come off the column as they were stored and go onto the wire unmasked — the hit's bounded to 64
runes, the cell's not bounded at all — while the excerpt beside them goes through a whole-document
mask. It carries a secret only if a payload puts a secret-shaped value in `hook_event_name`, which
the store takes verbatim. Masking it is a behaviour change and the length bound is what stands in
the meantime, so the gap is left open past Phase 4 deliberately rather than by omission.

**`events.id` is the second known perimeter, and a weaker one.** A `get_event` reply's and a search
hit's event id come off the column as they were stored and go onto the wire **neither masked nor
bounded** — where the session id in the same reply is masked and the event name is masked and then
bounded. `MaxEventIDBytes` bounds a *request*, not a reply. What separates it from `event_name` is
provenance: an event name is whatever a host's payload said, so a host controls it, while an id is
minted by the relay as a UUIDv7 and checked on the way in only for being non-empty. A secret-shaped
id therefore needs one of this user's **own** processes to write one — a hand-edited or corrupted
spool record is the route — which is a weaker threat than the one that left `event_name` open, and
is why this is recorded rather than closed. The fix is the one `list_sessions` already applies to an
id it refuses to truncate, which is to mask it. Raised by the Phase 6 review; backlog 29.

### 6.2 Fixtures are synthesised

Fixtures under `tests/fixtures/` copy the **shape** of real captures — JSON key paths, types,
nesting — and invent every value. No raw capture is ever committed.

**[verified]** This is not caution about hypotheticals. Real captures carry the user's work, not
just their username: Korean text alone appears in 228 of 902 captures through `tool_input.command`
(86), `tool_response.stdout` (68), `tool_input.content` (32), and `last_assistant_message` (28) —
that is real commands, real output, and real file contents. `origin` is public.

The cost of synthesis is drift: an invented fixture can stop matching what the host actually sends.
The guard is a **shape test** that reads `.capture/fixtures-raw/` locally and asserts every fixture's
key paths and types still occur in the real corpus. It is skipped when the corpus is absent, so
contributors can run everything else.

Synthetic secrets for the redaction break-it step are generated **at test runtime and never written
to the repository**. A committed `known-bad` file would put credential-shaped strings in a public
repository, which trips push protection and is indistinguishable from a real leak. The generator
itself needs a test: assert it produces a string the detector matches, so a generator that silently
emits something harmless cannot make the break-it step vacuous.

### 7.4 Decisions the re-measurement changed

1. **Peer verification does not need process creation time.** Zero PID reuse occurred inside the
   relay's 1 s budget. The rule instead is: verify the peer PID on the accepted connection and
   never cache it — at 48.93% overall reuse, a PID held past about a second means nothing.
2. **Checkpointing does not need a PASSIVE probe.** §5.4's escalation policy was inherited from a
   design with several connections. Cold `TRUNCATE` on an exclusive single connection is linear and
   cheap: 5.7 ms at 9.8 MiB, **32.5 ms at 66.1 MiB**, 140.5 ms at 258.3 MiB — roughly 0.54 ms/MiB,
   with `busy=0` every time. At the 64 MiB threshold that is 3% of the relay's entire budget. There
   is no other connection to block on.
3. **The 512 KiB field cap is not binding on real data**, and is now withdrawn because of it (§6,
   backlog 24). Corpus payloads: p50 1,182 B, p90 7,418 B, p99 32,936 B, max 171,764 B. The
   measurement is what decided the withdrawal rather than the implementation: a cap real traffic is
   two orders of magnitude below buys a code path nothing exercises, and the same numbers now
   justify `ipc.MaxFrameLen`, which is the only bound a stored payload has.
4. **Checkpointing has nothing to do with the `-shm`, and the reason the WAL is bounded is not
   checkpointing.** Both were assumed and both are wrong. The wal-index appeared on every reopen of
   an existing database whatever the WAL contained, so no schedule prevented it and the shutdown
   checkpoint could not either; what removed it was one DSN key (§5.4, §7.1). And the WAL was
   already bounded, by SQLite's own `wal_autocheckpoint`, which §5.4's DSN never disables. The
   checkpoint policy stays as specified —
   `TRUNCATE` is still the only thing that returns the file's space and still bounds crash recovery
   — but it is a reclamation policy, not the thing standing between the service and an unbounded
   file. §7.2's growth rate is what one checkpoint has to move; it is not the size the WAL reaches.

condition for proceeding, not a test case.

## 10. Open questions

The code answers these. They are listed so nobody mistakes silence for a decision.

1. ~~What `doctor` reports when the service is down, beyond failing with a clear message and exit 1.~~

   **Closed: §5.9.** `search`, `get_event`, `list_sessions`, `status` — each project-scoped, each

   the tool a model reaches for after a hit is "give me that event", which is why `get_event`

6. ~~Whether to move `journal_mode` out of the `_pragma` list and into the driver's `_journal_mode`
   key.~~ **Closed: done.** The DSN in §5.4 sets `_journal_mode=wal`, `locking_mode(exclusive)` is
   applied first, and no `-shm` is created in any of the three states §7.1 lists. The trade this
   question was holding open was accepted rather than avoided: one setting now reaches SQLite
   through a different mechanism from the other seven, I-11's name check was widened to recognise
   it, and the DSN a test pins as one exact string changed. What decided it is that the
   `SQLITE_OMIT_SEH=1` exposure is a fatal `throw("fault")` in a service whose whole job is not to
   lose events, this is the only route SQLite documents, and the ordering it now depends on is the
   driver's documented one where the previous ordering rested on an undocumented sort. Two costs
   are accepted with it and are permanent, not incidental: the connection cannot leave EXCLUSIVE
   without leaving WAL, and no second reader — `sqlite3.exe` included — can ever attach, which was
   already true in practice through the file lock and is now structural.
