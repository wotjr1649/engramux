## 0. 무엇을 만드는가

> Claude Code와 Codex의 세션 이벤트를 자동 캡처해, 사용자당 하나의 Go 서비스가 모든 동시 세션을
> 다중화하여 저장·검색·재주입하는 Windows-first 영속 메모리 엔진.

차별점은 **자동 hook 캡처** 하나다. [engram](https://github.com/Gentleman-Programming/engram)(Go,
SQLite+FTS5, ⭐6.2k)은 에이전트가 `mem_save`를 직접 호출해야 하고 MCP stdio 전용이다.
[claude-mem-lite](https://github.com/sdsrss/claude-mem-lite)는 hook 캡처를 하지만 Windows 미지원.
upstream `claude-mem`은 둘 다 하지만 Windows에서 만성적으로 깨진다.

### 확정된 범위 (사용자 승인 완료)

| 항목 | 결정 |
|---|---|
| 목적 | 개인 주력 엔진 겸 공개 OSS 제품 |
| 호스트 | Claude Code + Codex, 둘 다 1.0 |
| 이벤트 | 교집합 **11개**만 (Claude 31 ⊃ Codex 11, Codex-only 0) |
| claude-mem 마이그레이션 | **삭제** (원문서 §20 폐기) |
| LLM | **1.0 범위 밖.** 인터페이스도 만들지 않는다(§12) |
| 신뢰 경계 | **같은 Windows user SID는 신뢰 경계 안**(§5) |
| 순서 | **부분 순서**(§4) |

| 첫 slice | 대표 fixture 4개로 수직 관통(§11) |
| 개발 중 claude-mem | 유지 + shadow (DB 완전 분리) |

## 2. 호스트 계약 (실캡처 784건 기준)

### 2.1 이벤트 11개

`SessionStart` `SessionEnd` `UserPromptSubmit` `PreToolUse` `PostToolUse` `Stop`
`SubagentStart` `SubagentStop` `PreCompact` `PostCompact` `PermissionRequest`

두 호스트 모두 `async`를 지원하지만 **engramux는 사용하지 않는다.** async는 호스트의 직렬화를
포기하는 것이고(실측: async 24 이벤트 → inversion 101, sync → 0), 얻는 것이 없다.

### 2.2 실행 형태

| | Claude Code 2.1.246 | Codex 0.149.1 |
|---|---|---|
| `commandWindows` | **없음** | 있음 |
| exec-form `args` | 있음 → **셸 없이 직접 spawn** | 없음 |
| `shell` | `bash`\|`powershell` | 없음 |
| `additionalContextLimit` | 없음 | 있음 (기본 2500 토큰) |
| hooks 파일 최상위 키 | `hooks` | `description`, `hooks`만 |
| **hook trust** | 없음 | **변경된 hook은 사용자가 hash 기준으로 review/trust할 때까지 실행되지 않는다** |

Codex trust는 1.0 설치 절차의 필수 단계다. installer가 성공을 보고해도 capture가 무기한
꺼져 있을 수 있고, 업그레이드로 command hash가 바뀌면 다시 꺼진다.
→ installer에 명시적 `/hooks` review 안내, `doctor`는 `untrusted`를 **탐지만** 하고 고치지 않는다.
`--dangerously-bypass-hook-trust`는 사용 금지.

### 2.3 payload 필드

**실제 전역 교집합은 4개**다 — `cwd`, `hook_event_name`, `session_id`, `transcript_path`.
(rev.1은 `permission_mode`를 포함해 5개라고 적었으나 Codex `SessionEnd` 3/3건에 없다.)

| 필드 | Claude | Codex |
|---|:--:|:--:|
| 턴 상관 키 | `prompt_id` | `turn_id` |
| `effort:{level}` | O | — |
| `model` | — | O |
| `permission_mode` | O | 이벤트에 따라 부재 |
| `source`(SessionStart) / `reason`(SessionEnd) / `prompt`(UPS) | ? | O |
| `tool_name`/`tool_input`/`tool_use_id` | O | O |
| `agent_id`/`agent_type`/`agent_transcript_path` | O | O |

모든 adapter 필드는 포인터 또는 `omitempty`. 필수 검증은 교집합 4개로만 한다.

**호스트 판별은 argv가 아니라 payload 지문으로 한다.** `--host`는 검증되지 않는 CLI 인자다.
`prompt_id`+`effort` → claude-code, `model`+`turn_id` → codex (실캡처에서 교차 없음).
argv와 불일치하면 진단 로그 + fail-open. `payload.hook_event_name != --event`면 캡처만 하고
stdout은 무조건 빈 문자열.

**정규화 시 `prompt_id`와 `turn_id`를 둘 다 보존한다.** `turn_key`로 뭉개면 판별 신호가 사라진다.

### 2.4 출력 계약

- 캡처 이벤트: stdout 빈 문자열.
- 컨텍스트 이벤트(SessionStart): 정확히 1개 JSON document.
- **Codex `Stop`/`SubagentStop`은 exit 0에서 JSON을 기대한다**(공식 문서). host×event별
  무동작 출력 매트릭스를 pinned 바이너리로 블랙박스 검증한 뒤 확정한다.
- **`main()` 최상단에 `recover()` → `os.Exit(0)`.** Go panic은 exit 2를 내고, exit 2는 스펙이
  금지한 바로 그 호스트 차단 코드다(실측: 3종 panic 전부 exit 2). 미확보 fixture 이벤트가
  곧 panic 후보이므로 이 방어가 없으면 첫 `PreCompact`에서 호스트가 막힌다.
- `suppressOutput` 등 출력 키는 **바이너리 문자열 존재를 지원 근거로 삼지 않는다.** 이벤트별
  런타임 테스트 통과 시에만 사용.

### 2.5 호스트 강제 제약

- Codex `SessionEnd` hook timeout은 **3초로 강제 clamp**된다. 종료 flush 예산 3초.
- Codex `additionalContextLimit` 기본 2500 토큰. 컨텍스트 예산을 호스트별로 분리한다
  (`max_bytes_claude` / `max_bytes_codex`, Codex는 6,000바이트 이하).

## 3. 저장

### 3.1 원칙

`events`가 유일한 source of truth. 나머지는 재생성 가능한 derived state.
단 **재생성이 멱등이어야 한다** — 아래 `UNIQUE(source_type, source_id, processor_id)`가 그 조건이다.
(실측: 제약 없이 추출기를 3번 돌리면 `memory_items` 200 → 600, FTS도 600.)

### 3.2 rev.1 B-1 철회 — external content로 되돌린다

rev.1은 원문서 FTS DDL이 `no such column: T.facts`로 죽는 것을 보고 external content를 폐기했다.
**오진이었다. 진짜 결함은 컬럼명 불일치다** (FTS `facts` vs 테이블 `facts_json`).

| | 독립 테이블 (rev.1) | external content (컬럼명 일치) |
|---|---|---|
| `'rebuild'` | **성공을 반환하고 인덱스를 비운다.** 이후 `integrity-check`도 `ok` | 정상 |
| `'delete'` | `SQL logic error (1)` (메시지 없음) | 정상 |
| DELETE 후 rowid 재사용 | **`constraint failed (1555)` → 베이스 행이 안 들어감 = 데이터 유실** | 불가능 |
| 인덱스 배율 | 2.97x | **2.12x** |
| rev.1의 트리거 레시피 | `new.facts` — **같은 결함을 재현** | — |

즉 rev.1대로면 `engramux reindex --fts`가 검색 인덱스를 조용히 파괴한다.

### 3.3 연결 문자열 (모든 pooled connection에 적용)

```
file:<path>?_pragma=journal_mode(wal)
           &_pragma=foreign_keys(1)
           &_pragma=recursive_triggers(1)
           &_pragma=synchronous(3)
           &_pragma=busy_timeout(10000)
           &_pragma=journal_size_limit(67108864)
           &_pragma=secure_delete(1)
```

- `foreign_keys`는 **커넥션별**이다. `db.Exec("PRAGMA foreign_keys=ON")`은 풀 4개 중 1개만 켠다(실측).
- `recursive_triggers`가 OFF면 `INSERT OR REPLACE`가 DELETE 트리거를 건너뛴다.
  실측: 500 id에 2000 upsert → 베이스 500 / FTS 2000, **300% 팽창**, `integrity-check`는 `ok`.
- `synchronous`의 modernc 기본값은 NORMAL이고 **NORMAL은 전원 손실에 대해 내구성이 없다** →
  I-04가 거짓이 된다. FULL의 비용은 12,156 → 2,226 ev/s인데 **실측 필요량은 2 ev/s**다(§8). 공짜다.
- writer는 전용 `*sql.DB`에 `SetMaxOpenConns(1)`. reader는 별도 풀.
  실측: `MaxOpenConns(16)`는 p99 134.8ms/max 882ms, `(1)`은 p99 28.8ms/**max 40.5ms**이고
  처리량은 오히려 2배(1046 → 2156 ev/s).
- 백그라운드: 60초마다 그리고 `-wal`이 64MiB를 넘을 때마다 `PRAGMA wal_checkpoint(TRUNCATE)`.
  **모든 read 쿼리에 `context.WithTimeout`, `defer rows.Close()`를 린트로 강제한다.**
  실측: reader 하나가 고정되면 23MB 데이터가 **491MB WAL**이 된다. 누수된 `*sql.Rows` 하나면 충분하다
  (8,000 이벤트에 199MB). `journal_size_limit`은 해결책이 아니다(243MB까지 자람).

### 3.4 스키마

```sql
CREATE TABLE projects (
    id                TEXT PRIMARY KEY,          -- hash(repository_key, workspace_key), 결정적
    repository_key    TEXT NOT NULL,
    workspace_key     TEXT NOT NULL,
    canonical_root    TEXT NOT NULL,
    display_name      TEXT NOT NULL,
    git_remote_hash   TEXT,
    created_at_ms     INTEGER NOT NULL,
    last_seen_at_ms   INTEGER NOT NULL,
    UNIQUE(repository_key, workspace_key)
) STRICT;

CREATE TABLE sessions (
    id                   TEXT PRIMARY KEY,
    host                 TEXT NOT NULL,
    host_session_id      TEXT NOT NULL,
    parent_session_id    TEXT REFERENCES sessions(id),
    project_id           TEXT NOT NULL REFERENCES projects(id),
    status               TEXT NOT NULL DEFAULT 'active',
    started_at_ms        INTEGER NOT NULL,
    last_activity_at_ms  INTEGER NOT NULL,
    completed_at_ms      INTEGER,
    last_ingest_order    INTEGER NOT NULL DEFAULT 0,
    metadata_json        TEXT NOT NULL DEFAULT '{}',
    UNIQUE(host, host_session_id),
    CHECK (id = host || ':' || host_session_id)   -- id가 파생 가능 → upsert 패배가 불가능
) STRICT;

CREATE TABLE events (
    id                  TEXT PRIMARY KEY,
    host                TEXT NOT NULL,
    event_type          TEXT NOT NULL,
    session_id          TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    project_id          TEXT NOT NULL REFERENCES projects(id),
    ingest_order        INTEGER NOT NULL,          -- 도착 순서. 호스트 순서가 아니다(§4)
    idempotency_key     TEXT NOT NULL CHECK (length(idempotency_key) > 0),
    turn_key            TEXT,                      -- prompt_id 또는 turn_id (원본은 payload에 보존)
    tool_use_id         TEXT,                      -- Pre/PostToolUse 짝짓기용
    payload_json        TEXT NOT NULL,             -- redaction 통과 후의 바이트
    payload_sha256      TEXT NOT NULL,             -- **절단 전 원본** 바이트의 해시
    payload_truncated   INTEGER NOT NULL DEFAULT 0,
    payload_orig_bytes  INTEGER NOT NULL,
    privacy_class       TEXT NOT NULL,
    redaction_version   INTEGER NOT NULL,
    host_timestamp_ms   INTEGER,
    received_at_ms      INTEGER NOT NULL,
    schema_version      INTEGER NOT NULL,
    relay_version       TEXT NOT NULL,
    UNIQUE(host, idempotency_key),
    UNIQUE(session_id, ingest_order)               -- 위반이 prose가 아니라 엔진에서 드러난다
) STRICT;
CREATE INDEX idx_events_session_order ON events(session_id, ingest_order);
CREATE INDEX idx_events_project_time  ON events(project_id, received_at_ms DESC);
CREATE INDEX idx_events_tool_use      ON events(session_id, tool_use_id)
                                        WHERE tool_use_id IS NOT NULL;

CREATE TABLE observations (
    id                 TEXT PRIMARY KEY,
    source_event_id    TEXT NOT NULL REFERENCES events(id)   ON DELETE CASCADE,
    session_id         TEXT NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    project_id         TEXT NOT NULL REFERENCES projects(id),
```

### 3.5 FTS — external content, 컬럼명 일치

```sql
CREATE TRIGGER memory_items_ad AFTER DELETE ON memory_items BEGIN

CREATE TRIGGER memory_items_au AFTER UPDATE ON memory_items BEGIN
```

### 3.6 redaction 과 purge

**redaction은 `events` INSERT 앞 단계다.** 원문서 §21.2를 구속력 있게 복원한다.
저장되는 `payload_json`은 이미 redaction을 통과한 바이트이고, `redaction_version`을 함께 기록한다.

append-only의 정확한 의미를 재정의한다:

> `events`는 **삽입 전용**이다. 행은 삭제되지 않는다. 단 `purge`/`forget`은
> `payload_json`을 redaction 마커로 **in-place 치환**할 수 있다.
> `payload_sha256`, `ingest_order`, `idempotency_key`는 보존된다.

`PRAGMA secure_delete=1`이 필수다 — 없으면 치환된 원문이 free page에 남는다.
`ON DELETE CASCADE`가 있어야 프로젝트 단위 purge가 실행된다(실측: 없으면 `FOREIGN KEY constraint failed (787)`).

### 3.7 인제스트 트랜잭션

```sql
BEGIN IMMEDIATE;                       -- DEFERRED 는 SQLITE_BUSY 로 48% 유실(실측)

-- 1. idempotency 먼저. 재전송이 ingest_order 를 소모하면 유령 gap 이 생긴다.
SELECT ingest_order FROM events WHERE host = ?1 AND idempotency_key = ?2;
--   행이 있으면 → COMMIT 후 {"status":"committed"} ACK. **에러가 아니다.**

-- 2. upsert. project_id·last_ingest_order·status 는 절대 갱신하지 않는다.
INSERT INTO projects (...) VALUES (...)
ON CONFLICT(repository_key, workspace_key) DO UPDATE SET
  last_seen_at_ms = max(projects.last_seen_at_ms, excluded.last_seen_at_ms)
RETURNING id;                          -- DO NOTHING 은 행을 반환하지 않는다(실측)

INSERT INTO sessions (id, host, host_session_id, project_id, status,
                      started_at_ms, last_activity_at_ms)
VALUES (?1 || ':' || ?3, ?1, ?3, ?4, 'active', ?5, ?5)
ON CONFLICT(host, host_session_id) DO UPDATE SET
  started_at_ms       = min(sessions.started_at_ms,       excluded.started_at_ms),
  last_activity_at_ms = max(sessions.last_activity_at_ms, excluded.last_activity_at_ms);
  -- 의도적으로 빠짐: project_id(--resume 재배치 방지), last_ingest_order(리셋 방지), status

-- 3. 순번 발급
UPDATE sessions SET last_ingest_order = last_ingest_order + 1
WHERE id = ?1 || ':' || ?3 RETURNING last_ingest_order;

-- 4. 평범한 INSERT. UNIQUE 는 backstop 이고 dedup 은 1단계가 한다.
INSERT INTO events (...) VALUES (...);

COMMIT;                                -- 이 반환 뒤에만 ACK
```

**캡처 784건 중 689건(88%)이 자기 `SessionStart`보다 먼저 도착한다.** 12세션 중 6개는
`SessionStart`가 아예 없다. upsert-before-insert는 예외가 아니라 정상 경로다.

### 3.8 idempotency key

> **relay가 캡처 시점에, 첫 pipe write 전에 UUIDv7을 발급한다. spool 레코드에 그대로 저장하고,
> 모든 재전송 경로에서 바이트 단위로 재사용한다.**

payload 해시는 안 된다. Codex `SessionEnd`는 `{session_id, transcript_path, cwd,
hook_event_name, reason}`뿐이라 **진짜로 다른 두 이벤트가 조용히 하나로 합쳐진다**(실증).
실캡처에서 `(host, session, event, tool_use_id)`만으로는 35행이 6그룹으로 뭉개진다.

재전송 시 서비스는 `status: "committed"`를 반환한다. 에러를 반환하면 relay가 실패로 보고
무한 re-spool 한다.

## 4. 순서 — 부분 순서 모델

**I-06을 재정의한다.**

> 턴 간에는 순서를 보장한다. **턴 내부는 순서를 정의하지 않는다.**
> `ingest_order`는 서비스 **도착** 순서이며 호스트 발생 순서가 아니다.

근거: 두 호스트 payload에 순서 신호가 없다. `prompt_id`/`turn_id`는 턴 **식별자**이지
카운터가 아니고, relay는 매번 새 프로세스라 이전 이벤트를 모른다. 존재하지 않는 정보를
복원한다고 주장하지 않는다.

복원 가능한 것은 명시적으로 복원한다:
- `PreToolUse`/`PostToolUse`는 **`tool_use_id`로 짝짓는다.** 도착 순서와 무관하다.
- 턴 경계는 `turn_key`로 잡는다.
- spool import는 `ingest_order`를 뒤에 받는다 — 부분 순서 모델에서는 위반이 아니다.

`UNIQUE(session_id, ingest_order)`가 중복 발급을 엔진 레벨에서 막는다
(실측: 제약이 없으면 autocommit 경로가 640건 중 393건에 중복 순번을 **무오류로** 부여한다).

**FIFO 단일 writer는 채택하지 않는다.** inversion 0을 얻지만 relay p50이 31.5ms → 84.7ms가 되고,
위 정의상 보존할 대상이 애초에 없다.

## 5. 신뢰 경계와 프로세스

### 5.1 신뢰 경계 — 명시적 선언

> **같은 Windows user SID로 실행되는 모든 프로세스는 Engramux의 신뢰 경계 안에 있다.**
> Engramux는 그 경계 안에서 어떤 인증도 주장하지 않는다.

SECURITY.md에 이대로 적는다. 근거:

- 같은 SID 공격자는 `CreateNamedPipeW`로 두 번째 인스턴스를 만들어 payload를 가로챈다.
  실측: 스쿼터 8개 → **35/40(87.5%) 탈취**, 진짜 서비스는 5/40만 받았다.
- DACL로 막을 수 없다. `FILE_CREATE_PIPE_INSTANCE`를 사용자 ACE에서 빼면 공격자가 막히는
  **동시에 go-winio의 `Accept()`도 죽는다**(`makeServerPipeHandle(first=false)`가 매 Accept마다
  같은 권한을 요구). 같은 principal이면 ACL로 분리 불가 — 6칸 매트릭스로 실측.
- 그리고 그 공격자는 이미 `~/.claude/projects/**` 전사와 `~/.claude-mem/claude-mem.db`를
  직접 읽을 수 있다. 파이프가 새로 내주는 것이 없다.

**"양방향 신원 검증"은 삭제한다.** `GetNamedPipeServerProcessId`는 파이프 **생성자**의 PID를
반환한다 — 공격자 인스턴스(pid 3900)가 응답해도 진짜 서비스(pid 19828)의 PID와 이미지 경로를
돌려준다. 선의로 구현하면 **확신에 찬 false PASS**가 나온다.

남기는 것 (인증이 아니라 **사고성 오접속 탐지**):
- 서버가 `GetNamedPipeClientProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` →
  `GetProcessTimes`로 (pid, 생성시각) 쌍을 고정한 뒤 `QueryFullProcessImageName`.
  조회 실패는 **거부**로 처리한다. (PID 재사용은 2.3초에 5.75% 실측 — 생성시각 고정이 무료 케이스를 없앤다)
- 서명 검증은 **시작 시 1회**, (경로, volume+file ID, 최종수정, 크기)로 캐시.
  hook 임계경로에 두지 않는다 — 서명된 110MB 바이너리가 정상 상태 **51ms/회**, 그리고
  미서명 `go build` 산출물은 `TRUST_E_NOSIGNATURE`로 **항상 실패**한다.
- 서비스가 `GetNamedPipeHandleState`의 `lpCurInstances`를 자기 인스턴스 수와 대조해
  불일치 시 `doctor` red + loud fail. (실측: 스쿼터가 붙으면 2 → 3, 4, 10)

### 5.2 파이프 이름

```
\\.\pipe\engramux.v1.<UserSidHash>.<BootNonce>
```

- `<UserSidHash>`는 다중 사용자/RDP 충돌 회피용이다. **비밀이 아니며 보안 속성이 아니다.**
- `<BootNonce>`는 서비스 시작마다 새로 뽑는 난수다. 생성 **성공 후에만** discovery 파일에 공개한다.
  이것이 없으면 로그온 시 먼저 뜬 스쿼터가 이름을 선점해 **캡처를 영구히 조용히 죽인다**
  (실측: 선점 후 `ListenPipe` → `Access is denied`). Codex 자신도 `cxc-0KD8Ev-codex-app-server`처럼
  난수를 쓴다.
- discovery 파일은 §5.4의 명시적 DACL 아래 둔다.

### 5.3 싱글턴과 프로세스 수명

- **`service run`의 첫 문장은 `ListenPipe`다.** 실패하면 DB·spool·로그 파일을 **한 번도 열지 않고**
  즉시 종료한다.
  실측 근거: 구버전 S1이 살아 있는 상태에서 신버전 S2가 DB를 먼저 열고 `goose up`으로
  `ALTER TABLE`을 커밋한 뒤 `ListenPipe`에서 지면, S1의 다음 INSERT가
  `no column named legacy_col`로 죽고 **다음 로그온까지 캡처 전손**이 된다.
- **`ListenPipe` 독점은 listener 1개를 보장하지 worker 프로세스 1개를 보장하지 않는다.**
  파이프 소유권을 프로세스 수명 lease로 만든다: listener 오류·close → root context 취소 →
  즉시 프로세스 종료. 백그라운드 작업(projector, WAL checkpoint 티커)은 그 context를
  상속받아 함께 죽는다. 이것이 없으면 파이프 소유권을 잃은 프로세스가 DB 핸들과
  projector goroutine을 계속 쥔 채 살아남아, 새 서비스와 **동시에** 파생 상태를 쓴다.
- Named Mutex는 쓰지 않는다(64-way 경합에서 파이프 단독으로 승자 정확히 1, 실측).
- Scheduled Task XML에 `<MultipleInstancesPolicy>IgnoreNew</MultipleInstancesPolicy>` 명시.
- **service만 `-ldflags "-H=windowsgui"`로 빌드한다.** service는 Task Scheduler가 부모 콘솔
  없이 띄우므로 CUI면 콘솔이 생긴다. Go 기본이 `Subsystem=3(CUI)`이라 플래그가 없으면
  "console flash 0" 게이트가 달성 불가능하다.
- **relay는 CUI를 유지한다.** relay는 호스트가 띄우고, 호스트는 터미널에서 돌고 있어
  콘솔을 갖는다. CUI 자식은 부모 콘솔을 **상속**하므로 새 창이 생기지 않는다.
  실측 근거: hook 체인 전체가 이미 CUI다 — `node.exe`·`pwsh.exe`·`codex.exe`, 그리고
  이 프로젝트의 캡처 프로브가 CUI로 두 호스트에서 **901회** 실행되는 동안 콘솔 깜빡임이
  관측되지 않았다. GUI subsystem에서 상속된 stdout 파이프가 어떻게 동작하는지 확인할
  이유 자체가 없어졌고, 그래서 §2.4의 stdout 계약과 충돌할 여지도 없다.
- "console flash 0"은 직접 자동화할 수 없다. **대리 지표**: 빌드 산출물의 PE 헤더가
  service는 `Subsystem == 2`, relay는 `Subsystem == 3`인지 어서션한다.

### 5.4 파일 시스템

`%LOCALAPPDATA%\Engramux\`를 **설치 시 명시적 protected DACL로 생성한다**:
`D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;<user SID>)`.

기본 상속을 쓰면 안 된다 — 이 머신의 `%LOCALAPPDATA%`에는
`CodexSandboxUsers:(I)(OI)(CI)(RX)`가 상속돼 있어, **Codex sandbox 계정이 메모리 DB와
MCP 토큰을 읽게 된다**(원문서 §21.1이 요구했고 rev.1이 뺐다).

Scheduled Task는 같은 SID가 수정할 수 있다(마스커레이드 가능). 권한 상승은 아니지만 탐지는 한다 —
`doctor`가 등록된 태스크의 `<Command>`/`<Arguments>`/`<RunLevel>`/`<LogonType>`/
`<MultipleInstancesPolicy>`를 기대값과 대조한다.

### 5.5 spool

- relay는 이벤트마다 **임시 파일 하나**에 쓰고 flush한 뒤 고유 이름으로 atomic rename 한다.
  공용 append 파일을 쓰지 않는다.
- import·retention·삭제는 **서비스만** 한다. DB 커밋 후에만 파일을 지운다.
- spool 레코드는 relay가 발급한 UUIDv7을 그대로 담는다.
- spool로 들어온 이벤트는 `source='spool'`로 구별한다. 파이프 경유와 동등하게 취급하지 않는다.

### 5.6 프레임

`[4B LE length][UTF-8 JSON]`. **길이를 검증한 뒤에 할당한다** — 공격자 `uint32`를 그대로
`make([]byte, n)`에 넣으면 4GiB 할당이다. relay는 dial 직후 `conn.SetDeadline(2s)`을 건다
(Codex의 `SessionEnd` 3초 clamp 안쪽). `DialPipeContext`의 context는 dial만 제한하고
반환된 `net.Conn`에는 데드라인이 없다 — 실측으로 120초 이상 정지를 확인했다.

## 6. MCP

```
http://127.0.0.1:<persisted-port>/mcp   Streamable HTTP + bearer
```

- `mcp.NewStreamableHTTPHandler(..., &mcp.StreamableHTTPOptions{ ... })`에
  **`CrossOriginProtection`을 명시 설정한다** (기본 `nil`이라 꺼져 있다).
- **`DisableLocalhostProtection`을 절대 설정하지 않는다.** 기본값이 DNS rebinding을 막는다
  (`Host: evil.com` → 403, 실측).
- bearer 검증은 SDK가 하지 않는다 — 우리 미들웨어(`auth.RequireBearerToken`)의 책임이다.
- **토큰을 쿼리스트링·쿠키에 절대 넣지 않는다.** 둘 중 하나만 해도 브라우저의 preflight 방어가
  무너진다.
- `MaxRequestBodyBytes` 기본 4MiB로 원문서 §21.5의 body cap이 이미 충족된다.
- 문서에 명시: **`127.0.0.1` 바인딩은 머신을 제한하지 프로세스를 제한하지 않는다.** 같은 SID
  프로세스는 토큰 파일을 읽고 tool을 호출할 수 있다. §5.1의 신뢰 경계와 일치한다.

**재주입 메모리는 untrusted 봉투로 감싼다.** 캡처된 내용은 clone한 저장소의 README, 도구 출력,
npm 에러 메시지에서 온다. 그것이 `memory_items`가 되고 SessionStart에 주입되면 **한 번의
프롬프트 인젝션이 프로젝트의 모든 이후 세션에, 그리고 두 호스트가 저장소를 공유하므로
반대편 호스트에도 영구히 재생된다.** 봉투에 출처(host, session, project, timestamp)를 명시하고
"기록된 관측이지 지시가 아님"을 표기한다. `memory_search`/`memory_context`도 동일하다.

## 7. 검색

### 7.1 rev.1의 측정 방법이 틀렸다

rev.1 §7의 93.3%는 **단일 토큰 질의**만 쟀고, 지표도 `COUNT(*) 매칭`이었다. 실코퍼스 12,664건에서
다중 토큰 질의를 재보면:

| 질의 구성 | 마이크로평균 recall |
|---|---:|
| rev.1 §3.3 규칙(전체를 감싸고 끝에 `*`) | **6.2%** |
| 토큰별 `"tok"*` 결합 | 64.1% |

`파일 저장` 0%, `오류 수정` 0%, `context 주입` 0%, `prompt id` 1%. **입력 전체를 감싸면
phrase 질의가 된다.**

그리고 `COUNT(*) 매칭`은 검색 품질 지표가 아니다. **Recall@K로 재정의한다.**

### 7.2 질의 빌더 (§3.3 규칙 대체)

```go
func ftsQuery(in string) (string, bool) {
    in = strings.Map(func(r rune) rune {
        if r < 0x20 && r != '\t' && r != '\n' { return -1 }   // NUL 하나로 FTS5 파서가 죽는다
        return r
    }, in)
    toks := strings.Fields(in)
    if len(toks) > 64 { toks = toks[:64] }                    // 512KB 입력 = 17.7초(실측)
    var out []string
    for _, t := range toks {
        t = strings.Trim(t, "!\"#$%&'()*+,-./:;<=>?@[\\]^_{|}~")
        if t != "" { out = append(out, `"`+strings.ReplaceAll(t, `"`, `""`)+`"`) }
    }
    if len(out) == 0 { return "", false }                     // `""*` 를 절대 내보내지 않는다
    out[len(out)-1] += "*"
    return strings.Join(out, " "), true
}
```

- 토큰이 비면 FTS를 건너뛰고 최근순 페이지를 반환한다. 빈 질의가 "결과 없음"과 구별되지 않으면 안 된다.
- 구두점 트림이 없으면 `+alpha`가 truth 0인데 2건을 반환한다(실측).
- **저장 시에도 제어문자를 제거한다.** 저장된 NUL은 SQL `length()`를 505바이트 → **4**로 만든다.
  컨텍스트 예산 계산이 조용히 절단된다. 크기 계산에 `TEXT`의 `length()`를 쓰지 않는다.

### 7.3 camelCase

`unicode61`은 `fooBar`를 `foo`/`Bar`로 나누지 않으므로 `bar*`가 `fooBar`를 못 찾는다.
`memory_items.body_norm`에 camelCase·snake_case를 공백으로 분해한 사본을 넣고 FTS에 함께 색인한다.

### 7.4 Phase 5b 게이트 — 숫자와 코퍼스

**고정 relevance 코퍼스** `tests/fixtures/search/corpus-v1/`:
- 문서 `docs.jsonl` — 실캡처에서 결정적 추출로 만든 `memory_items` **2,000건**을 고정 스냅샷으로
  커밋한다. redaction(§3.6)을 통과한 것만. 생성은 1회이고 이후 불변이다.
- 질의 `queries.jsonl` — **40개**, 아래 4클래스에 10개씩. 각 질의에 정답 `memory_id` 목록을
  **수동 라벨링**해서 함께 커밋한다. 라벨링 주체는 이 프로젝트 관리자다.

| 클래스 | 예 | 게이트 |
|---|---|---|
| KO 2글자 단일 토큰 | `세션` `파일` `오류` `설정` `검증` | **Recall@20 ≥ 0.80** |
| KO 2토큰 | `파일 저장` `세션 시작` `오류 수정` | **Recall@20 ≥ 0.70** |
| KO 질의 측 조사 변형 | `저장을` `세션에서` `파일을` | **Recall@20 ≥ 0.70** |
| camelCase 부분일치 | `Codec`→`DeviceCodec`, `Start`→`SessionStart` | **Recall@20 ≥ 0.90** |

마이크로평균이 아니라 **클래스별로** 통과해야 한다. 마이크로평균은 rev.1이 한국어 실패를
영어 대량 매칭으로 가린 방식이므로 쓰지 않는다.

**지연 게이트:** 위 코퍼스 2,000건 + `queries.jsonl` 40개를 순차 실행,
동시 reader 0, warm(2회 예열 후 측정), 단일 프로세스 기준 **P95 ≤ 50ms**.
100k 규모 목표는 1.0 게이트가 아니다 — 실측 도착률(§8)로 100k 도달까지 수개월이 걸린다.

## 8. 성능 (실측)

| 항목 | 측정 |
|---|---|
| **실제 도착률** | 가장 바쁜 Claude 세션 **14.8 events/min**(2176초 관측), Codex 4.9/min. **8 동시 세션 ≈ 2 ev/s** |
| 인제스트 (writer 1개, synchronous=FULL) | 2,226 ev/s — 필요량의 **1000배** |
| relay spawn+pipe+commit+ACK (순차) | p50 11.3ms / p95 14.2ms |
| 인제스트 p95 / max (`MaxOpenConns(1)`) | 16.9ms / **40.5ms** |
| hook stdin 크기 (최종 N=901) | p50 1,147B / p95 16,853B / p99 35,121B / **max 171,764B** |
| 512KiB 필드 상한 초과 | **0건** (최대가 상한의 33%) |
| Go relay vs node hook spawn | 11.3ms vs 56~60ms |
| 바이너리 | modernc sqlite 9.6MB, +goose 12.2MB |

**rev.1 §8의 max 12.9KB는 틀렸다.** N=782에서 5.5%가 그 값을 넘고 최대는 78.7KB다.

**동시성 게이트를 다시 쓴다.** rev.1의 "100 동시 논리 세션"은 측정 대상이 틀렸다.
100개를 barrier로 동시 spawn하면 spawn p50이 74.6ms가 되지만(실측), 실제 도착률은 2 ev/s다.
현실적 burst는 병렬 tool batch와 서브에이전트로 **5~20** 수준이다. 게이트를
"16 동시 relay에서 dial 실패 0, `-wal` 64MiB 이하 유지"로 바꾼다.
원문서 §7.3의 `pipe connect deadline 25ms`는 **200ms로 올린다**(32 동시에서 11.6% 초과 실측).

## 9. 미검증 (Phase 0에서 해소)

1. **`schtasks` 비관리자 등록** — **Phase 0 blocker.** MS 문서는 로컬 태스크 등록에
   Administrators를 요구한다고 적혀 있고, 이 머신에는 `Authenticated Users:(CI)(W,Rc)`와
   사용자 등록 태스크 실물이 있다. 양쪽 다 결정적이지 않다(그 태스크가 elevated로 만들어졌을 수 있음).
   **표준 사용자 계정에서 실측하기 전까지 "관리자 불필요"를 문서에서 삭제한다.**
   실패 시 대안: 설치 시 1회 elevation, 또는 `HKCU\...\Run` + relay의 bounded on-demand start.
2. `schtasks /Create /XML` 인코딩 — UTF-16LE+BOM으로 쓰고 재조회로 검증.
3. Codex `matcher` 의미(정규식/글롭), 비-PreToolUse 이벤트 적용 여부.
4. Codex `additionalContextLimit` 초과 시 절단인가 거부인가.
5. host×event별 **비어 있지 않은** 출력 매트릭스. **빈 출력은 이미 확인됐다** — 캡처 프로브가
   11개 이벤트 전부에서 stdout에 아무것도 쓰지 않고 두 호스트에서 901회 실행되는 동안
   hook 오류가 없었다(Codex `Stop` 포함). Codex 공식 문서가 `Stop`/`SubagentStop`에 JSON을
   기대한다고 적었지만 **빈 출력이 실제로 통과한다.** 남은 것은 컨텍스트 JSON을 실제로
   내보낼 때의 수용 범위다.
6. 미확보 fixture 10종: 양쪽 `PreCompact`/`PostCompact`/`PermissionRequest`,
   Claude `SessionStart`/`SessionEnd`, Codex `SubagentStart`/`SubagentStop`.
   **일괄 확보하지 않는다** — Phase 2가 이벤트별로 게이트하므로 해당 adapter를 켜는
   시점에 그 fixture만 모은다(§15.2).
7. 전원 손실 내구성 — `synchronous=FULL`의 pragma 값과 비용은 측정했으나 crash injection 설비가 없다.
8. `upstream #3692` 메커니즘 — 증상은 이 머신 로그에 11분간 실재하나 socket handle inheritance는
   Node 24.19/Bun 1.3.14 4개 조건에서 재현 실패. **Named Pipe 설계는 메커니즘과 무관하게 유효하다.**

> rev.2 초안의 §9.7(`-H=windowsgui` relay stdout)은 **삭제됐다.** 측정으로 답한 것이 아니라
> 질문이 성립하지 않음을 확인했다 — relay에 GUI subsystem이 필요하다는 전제가 틀렸다(§5.3).

### 14.1 핵심 타입

```go
// internal/event/envelope.go
package event

type Host string
const (HostClaudeCode Host = "claude-code"; HostCodex Host = "codex"; HostUnknown Host = "unknown")

type Type string
const (
    SessionStart Type = "SessionStart"; SessionEnd Type = "SessionEnd"
    UserPromptSubmit Type = "UserPromptSubmit"
    PreToolUse Type = "PreToolUse"; PostToolUse Type = "PostToolUse"
    Stop Type = "Stop"
    SubagentStart Type = "SubagentStart"; SubagentStop Type = "SubagentStop"
    PreCompact Type = "PreCompact"; PostCompact Type = "PostCompact"
    PermissionRequest Type = "PermissionRequest"
    TypeUnknown Type = "unknown"
)

type PrivacyClass string
const (Public PrivacyClass = "public"; Sensitive PrivacyClass = "sensitive"; Redacted PrivacyClass = "redacted")

// Envelope 는 relay 가 만들어 파이프로 보내는 유일한 구조체다.
// 원문서 §7.4 의 EventEnvelope 를 대체한다 — 그 구조체에는
// PayloadTruncated/PayloadOrigBytes/RedactionVersion/TurnKey/ToolUseID 가 없고
// Sequence 의 의미도 §4 에서 바뀌었다.
type Envelope struct {
    Version          uint16          `json:"version"`            // 현재 1
    IngestID         string          `json:"ingest_id"`          // UUIDv7. idempotency key(§3.8)
    Host             Host            `json:"host"`
    EventType        Type            `json:"event_type"`
    HostSessionID    string          `json:"host_session_id"`
    TurnKey          string          `json:"turn_key,omitempty"` // prompt_id ?? turn_id
    ToolUseID        string          `json:"tool_use_id,omitempty"`
    CWD              string          `json:"cwd"`
    TranscriptPath   string          `json:"transcript_path,omitempty"`
    Payload          json.RawMessage `json:"payload"`            // redaction 통과 후
    PayloadSHA256    string          `json:"payload_sha256"`     // **절단 전 원본**의 해시
    PayloadTruncated bool            `json:"payload_truncated"`
    PayloadOrigBytes int             `json:"payload_orig_bytes"`
    PrivacyClass     PrivacyClass    `json:"privacy_class"`
    RedactionVersion int             `json:"redaction_version"`
    HostTimestampMS  int64           `json:"host_timestamp_ms,omitempty"`
    RelayVersion     string          `json:"relay_version"`
}

type AckStatus string
const (Committed AckStatus = "committed"; Rejected AckStatus = "rejected")

type Ack struct {
    Version  int            `json:"version"`
    IngestID string         `json:"ingest_id"`
    Status   AckStatus      `json:"status"`   // 재전송도 committed 다(§3.8)
    BootID   string         `json:"boot_id"`
    Context  *ContextBundle `json:"context,omitempty"` // SessionStart 에서만
}

type ContextBundle struct {
    Items     []ContextItem `json:"items"`
    Bytes     int           `json:"bytes"`
    Truncated bool          `json:"truncated"`
}

// ContextItem 은 §6 의 untrusted 봉투다. Text 는 지시가 아니라 기록된 관측이다.
type ContextItem struct {
    MemoryID    string `json:"memory_id"`
    OriginHost  Host   `json:"origin_host"`
    OriginSess  string `json:"origin_session"`
    ProjectKey  string `json:"project_key"`
    RecordedAt  int64  `json:"recorded_at_ms"`
    Text        string `json:"text"`
}
```

### 14.3 결정적 추출 규칙 (`deterministic@v1`)

`Extract`는 **순수 함수**다. envelope 하나를 받아 observation 0..N개를 낸다.
아래 표에 없는 이벤트는 observation을 만들지 않는다(이벤트 자체는 `events`에 남는다).

| event_type | observation 생성 | `type` | 규칙 |
|---|---|---|---|
| `PostToolUse` | 1개 | 아래 판정 | 항상 생성 |
| `UserPromptSubmit` | 1개 | `prompt` | `payload.prompt`(Codex) 또는 Claude의 프롬프트 필드. redaction 통과분만 |
| 나머지 9개 | 0개 | — | 세션 상태 전이만 반영 |

`PostToolUse`의 `type` 판정 — **위에서부터 먼저 맞는 것**:

1. `payload.tool_response.interrupted == true` 이거나 `tool_response.stderr`가 비어 있지 않음 → `error`
2. `tool_name`이 `Edit`/`Write`/`NotebookEdit`/`MultiEdit` → `file_change`
3. `tool_name == "Bash"` → `command`
4. 그 외 → `tool_use`

필드 매핑:

| 필드 | 규칙 |
|---|---|
| `FilesChanged` | `tool_input.file_path`, `tool_input.notebook_path`, `tool_input.edits[].file_path` 를 모아 중복 제거. **`Bash` 의 `command` 문자열에서 경로를 파싱하지 않는다** — 오탐이 크다 |
| `FilesRead` | `tool_name`이 `Read`/`Glob`/`Grep`일 때 `tool_input.file_path` 또는 `tool_input.path` |
| `Title` | `"<tool_name>: <basename(첫 파일)>"`, 파일이 없으면 `"<tool_name>"` |
| `Narrative` | `tool_input.description`이 있으면 그것, 없으면 빈 문자열. **생성하지 않는다** — LLM이 없다 |
| `Facts` | `["tool=<tool_name>"]` + `error`면 `"exit=nonzero"` + `file_change`면 `"files=<n>"` |
| `Concepts` | `FilesChanged`+`FilesRead`의 확장자 집합(`.go`, `.md` …)과 디렉터리 첫 세그먼트 |
| `Confidence` | 결정적 추출은 상수 `1.0` |
| `body_norm` | `Title`+`Narrative`+`Facts`를 이어붙인 뒤 camelCase·snake_case를 공백으로 분해(§7.3) |

`memory_items` 한 행은 observation 한 개에 1:1 대응한다.
`source_type='observation'`, `source_id=observations.id`, `processor_id='deterministic@v1'`.

### 15.2 미확보 10종 유도 시나리오

현재 `.capture/fixtures-raw` 902건의 실제 분포:
`claude-code` PreToolUse 322 · PostToolUse 307 · SubagentStop 119 · Stop 12 ·
UserPromptSubmit 10 · SubagentStart 5 · PermissionRequest 1 /
`codex` PreToolUse 39 · PostToolUse 39 · SessionEnd 13 · Stop 9 · SessionStart 9 · UserPromptSubmit 9.

| 미확보 | 유도 방법 |
|---|---|
| `claude-code` SessionStart / SessionEnd | 캡처 hook을 다시 걸고 Claude Code 세션을 새로 열었다 닫는다 |
| 양쪽 PreCompact / PostCompact | 긴 세션에서 `/compact` 수동 실행 |
| `codex` PermissionRequest | `codex exec`가 아니라 승인이 필요한 모드의 대화형 Codex 세션 |
| `codex` SubagentStart / SubagentStop | `multi_agent`가 켜진 Codex 세션에서 서브에이전트 유발 |

Phase 2는 이벤트별로 게이트하므로 **10종을 한 번에 모을 필요가 없다.** 해당 이벤트 지원을
켜는 시점에 그 fixture만 있으면 된다.

### 15.3 secret fixture 세트
